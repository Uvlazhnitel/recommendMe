# DATA_AND_DEPLOYMENT.md — данные, сервер и API

## 1. Архитектура без лишних сервисов

```text
Браузер (ПК / телефон, домашняя сеть)
         │
    Next.js (TypeScript)
         ├── UI: рекомендации / оценка / библиотека
         ├── серверные обработчики (проверка входных данных)
         ├── SQLite в постоянной папке
         ├── TMDB API (поиск и сведения о фильмах)
         └── LLM API (профиль / кандидаты / итоговый отбор)
```

**Один контейнер приложения + SQLite-файл, без отдельного контейнера базы данных.** Docker Compose — для предсказуемого запуска на домашнем сервере, а не для микросервисной архитектуры. Весь вызов внешних API выполняется на сервере.

Подфаза 5.1: изолированный тестовый Docker на homeserver, только синтетические данные и пустые API-настройки. Постоянный bind `/app/data`, фиксированный `/app/data/movies.sqlite`, journal и lock рядом с базой. Порт публикуется только на loopback; доступ через SSH-туннель. Production start не выполняет миграций, health открывает SQLite readonly. Операционные команды, backup API + согласованный offline journal и восстановление — в `docs/HOMESERVER_DEPLOYMENT.md`. Реальная миграция и доступ телефона по LAN не выполняются до отдельного решения 5.2.

Подфаза 5.2: настоящая библиотека и серверные настройки перенесены в отдельную основную установку `$HOME/apps/recommendme/`. Исходная schema 5 сохранена без миграций; локальный источник/CSV/.env.local не менялись. Сервер — единственная рабочая копия для дальнейших оценок. Частный Tailscale Serve HTTPS на 12443 проксирует loopback 45151; существующие Serve/Funnel-маршруты не изменены. Restore поддерживает явный --relocate-from: проверяет исходный canonical path по manifest и переименовывает только хеш-каталог journal, сохраняя JSON/request_id/result_id. Обычный restore без флага остаётся строгим. Приёмка: 198 тестов, перенос/проверка всех таблиц, offline replay без сети/ключей, HTTPS/Origin и restart/recreate; новых OpenAI/TMDB API-запросов 0. Эксплуатация и backup описаны в docs/HOMESERVER_DEPLOYMENT.md.

## 2. Исходные CSV Letterboxd

Файлы владельца: `watched(6).csv` и `ratings(6).csv`.

```text
watched: Date, Name, Year, Letterboxd URI
ratings: Date, Name, Year, Letterboxd URI, Rating
```

Проверенные исходные данные:
- 830 уникальных строк в `watched`;
- 519 уникальных строк в `ratings`;
- все 519 оценённых входят в `watched`;
- 311 просмотрены без оценки;
- `Rating` принимает звёзды с шагом 0,5 (в текущем файле встречаются 1,5–5).

Правила `seed`:
1. Считать файлы UTF-8, CSV по заголовкам, не по порядку колонок.
2. Объединить по **`Letterboxd URI`**, название+год сохранить как атрибуты.
3. Все 830 записей `watched` перенести в базу — **включая сериалы, короткометражки и записи без TMDB ID**, чтобы сохранить историю и корректно исключать просмотренное.
4. Для 519 с оценками поставить `watched=1`, `rating_100=round(stars*20)`, `original_rating_stars=stars`, `rating_source='letterboxd'`.
5. Для остальных: `watched=1`, `rating_100=NULL`.
6. `Date` из watched хранить как `letterboxd_date`, из ratings — отдельно как `letterboxd_rating_date`; эти даты могут отличаться. `watched_at` не заполнять без подтверждения фактической даты просмотра.
7. Для TMDB сопоставлять название/год, проверять неоднозначные случаи. Нераспознанные фильмы **не удалять**: сохранять без `tmdb_id`, вывести отчёт.
8. Повторный запуск не создаёт дубликатов. Уже существующие строки `user_movies` сохраняются целиком, включая вручную очищенные оценки, просмотр, скрытие и timestamps. Существующие метаданные фильмов не заменяются; допускается однозначная привязка отсутствующего URI.

Это **только скрипт разработчика**. Ни UI импорта, ни пользовательской загрузки файлов, ни регулярного сканирования директории не требуется.

### Фактическая команда первоначального импорта (подфаза 1.3)

```sh
npm run seed:letterboxd
# Либо передать оба пути явно:
npm run seed:letterboxd -- --watched /path/watched.csv --ratings /path/ratings.csv
```

По умолчанию используются `data/import/watched(6).csv` и `data/import/ratings(6).csv`. Скрипт читает окружение через `@next/env`, проверяет файлы, UTF-8 и CSV до открытия БД, затем создаёт backup через SQLite backup API в `data/backups/`, применяет миграции и записывает допустимые строки одной IMMEDIATE-транзакцией. Отказ backup не допускает изменений. Ошибка SQL откатывает импорт; уже успешно применённая миграция при этом остаётся. Отчёт сохраняется в `data/import-reports/` и выводится в терминал.

Структурные ошибки CSV/заголовков прекращают импорт без записи. Ошибочные строки, конфликтующие дубликаты и неоднозначные совпадения пропускаются с источником, номером записи и причиной; остальные строки импортируются, статус отчёта — partial, exit code — 1. Точные дубликаты одного источника схлопываются. Без URI используется только однозначное нормализованное название + известный год; разные известные URI не объединяются. При отсутствии URI и года запись пропускается. Строки только из ratings также означают просмотр и учитываются отдельно в отчёте.

Оценка — точное число 0..5 с шагом 0,5, умноженное на 20; пустая оценка — NULL. Импорт сохраняет всю историю без определения типа произведения (`unknown`, `tmdb_id=NULL`). Сопоставление с TMDB отнесено к подфазе 1.4. Автотесты используют синтетические CSV и временные базы; реальные CSV, отчёты, backup и SQLite исключены из Git.

## 3. Простая схема SQLite (ориентир, не догма)

Ниже концептуальные сущности; Codex вправе сделать компактную эквивалентную схему, если поведение и ограничения сохранены. Обязательны миграции/версионирование схемы, устойчивые идентификаторы и целостность данных.

### `movies` — каталог

| Поле | Назначение |
| --- | --- |
| `id` | Локальный первичный ключ. |
| `tmdb_id` | Уникальный ID фильма TMDB; `NULL` для неразрешённых записей CSV и TV. |
| `letterboxd_uri` | Уникальная ссылка Letterboxd; допускается `NULL` для новых фильмов. |
| `title`, `release_year` | Название/год; не использовать их единственным уникальным ключом. |
| `media_type` | `movie`, `tv`, `unknown` — особенно для импорта. |
| `runtime_minutes` | Длительность либо `NULL`. |
| `overview`, `genres_json`, `poster_path`, `backdrop_path` | Подтверждённые метаданные для UI/AI. |
| `tmdb_vote_count`, `tmdb_popularity` | Вспомогательные сигналы, не гарантия качества. |
| `metadata_updated_at` | Когда успешно обновляли информацию из TMDB. |
| `tmdb_title`, `original_title`, `tmdb_release_year` | Названия/год TMDB отдельно от исходных полей Letterboxd. |
| `original_language`, `tmdb_vote_average` | Язык оригинала и рейтинг TMDB 0–10, nullable. |
| `directors_json`, `credits_json` | Режиссёры (массив) и основные cast/crew (объект), nullable JSON. |
| `tmdb_enrichment_status`, `tmdb_attempted_at` | pending/matched/not_found/ambiguous/error и UTC-время попытки. |

### `user_movies` — твоя история

| Поле | Назначение |
| --- | --- |
| `movie_id` | Уникальный FK на `movies` (одна актуальная запись на фильм). |
| `watched` | `true/false`. |
| `rating_100` | **Целое 0–100 или `NULL`**; check constraint. |
| `review_text` | Необязательный исходный текст впечатлений; nullable, миграция 6, до 2000 символов, независим от оценки. |
| `original_rating_stars` | Исходные Letterboxd звёзды, nullable. |
| `rating_source` | `letterboxd` / `manual` / `none` (или эквивалент). |
| `not_interested` | Явное отклонение рекомендации, **не оценка**. |
| `watched_at` | Подтверждённая дата просмотра, nullable; не выводится из даты экспорта. |
| `letterboxd_date` | Исходная дата из watched, nullable. |
| `letterboxd_rating_date` | Исходная дата из ratings, nullable; миграция №2. |
| `created_at` | Дата добавления персональной записи. |
| `updated_at` | Для свежих изменений и обновления AI-профиля. |

Обязательные правила: `rating_100 = 0` — оценка; `NULL` — нет оценки. `not_interested=1` не делает фильм просмотренным и не понижает рейтинг. Изменение оценок не должно создавать вторую строку для фильма.

### `taste_profile` — кешированная текстовая модель вкуса

- Одна актуальная запись с `id=1`: `profile_json`, `created_at`, `updated_at`.
- JSON валидируется SQLite. Содержимое разъяснено в `RECOMMENDER.md`; сведения о снимке оценок/версии профиля при необходимости входят в JSON.
- Периодическое обновление; после новых оценок можно пользоваться старым профилем, дополняя его последними изменениями. Генерация профиля в подфазе 1.2 не реализуется.

### `recommendations` — история показов

По уточнённому заданию подфазы 1.2 вместо `recommendation_batches` / `recommendation_items` используется одна таблица:
- `id`, `movie_id`, `recommended_at`, nullable `why_fit` и `possible_mismatch`, `rejected` (0/1).
- Один фильм может быть предложен несколько раз. Индекс `(movie_id, recommended_at)` помогает проверять прошлые показы.
- `rejected` фиксирует отклонение конкретного показа; `user_movies.not_interested` хранит глобальное скрытие фильма. Оба состояния независимы от просмотра и оценки; будущая операция отклонения должна менять их в одной транзакции, не меняя просмотр/оценку.
- Группировка подборок, модель и usage не добавлены в этой подфазе; необходимые расширения хранения будут определены при реализации рекомендателя.

### Создание и обновление схемы

`npm run db:init` явно применяет SQL-миграции из `migrations/` и выводит текущую версию. Версия хранится в `PRAGMA user_version`, миграции выполняются в одной `BEGIN IMMEDIATE` транзакции. Повторный запуск сохраняет данные; неизвестная более новая версия приводит к ошибке. Подключение и `/api/health` не запускают миграции.

Все четыре таблицы — `STRICT`; каждое соединение включает `foreign_keys=ON`, удаление связанных фильмов запрещено (`RESTRICT`). Рейтинг — целое 0–100 или NULL; исходные звёзды — 0–5 с шагом 0,5. Неизвестные значения nullable. Даты создания/обновления — UTC с миллисекундами; SQL-триггеры меняют `updated_at` персональной записи/профиля при изменении содержательных полей. Название и год не являются уникальным ключом; разрешены несколько NULL внешних идентификаторов. `genres_json` — валидный JSON-массив или NULL.

**Не добавлять** отдельную таблицу пользователей, роли, подписки, сложное событийное хранилище, десятки индексов «на будущее».

## 4. Минимальные серверные операции

Точные URL и имена функций выбирает Codex, но достаточно таких операций:

| Действие | Вход | Выход |
| --- | --- | --- |
| Получить библиотеку | строка поиска/пагинация | список фильмов со статусом и оценкой |
| Найти фильм TMDB | название | список с названием, годом, ID, постером |
| Сохранить фильм | `tmdb_id`, `watched`, `rating_100` nullable | сохранённая запись |
| Исправить/очистить оценку | локальный ID, `rating_100` nullable | сохранённая запись |
| Получить рекомендации | запрос генерации | 1–5 валидных карточек |
| Отклонить предложение | локальный ID | `not_interested=true` |

Вся валидация значений **на сервере**: диапазон 0–100, настоящее `NULL`, корректный ID, правдоподобные данные из TMDB. Не доверять только клиенту или JSON от LLM.

## 6. Docker Compose и постоянное хранение

- В фазе 5 создать `Dockerfile` и минимальный `compose.yaml`: **один сервис `app`**. По уточнённой подфазе 1.5 Docker исключён из приёмки фазы 1.
- SQLite и бэкапы держать за пределами образа, например хостовый путь `./data/` → `/app/data/`. Убедиться, что у процесса есть права записи.
- Порт приложения должен быть доступен устройствам **в доверенной домашней сети**; конкретную карту портов определить на сервере.
- При обычном `docker compose up -d --build` старые оценки **не перезаписываются** и не исчезают.
- Начальное заполнение базы выполняется отдельной явной командой в контейнере или на хосте — не каждый раз автоматически при старте.
- Публичное открытие порта/проброс на роутере в MVP **не делать**. Для доступа извне позже можно отдельно решить вопрос защищённого VPN (например, Tailscale) и доступа к приложению.

## 7. Бэкап и восстановление

- В фазе 5 подготовить **простой проверенный способ** резервного копирования базы. Для SQLite предпочтительно использовать SQLite backup API / `.backup` (или делать копию после остановки приложения), а не копировать активный файл без учёта WAL.
- Бэкап должен храниться отдельно от основной БД, например в другом каталоге/накопителе домашнего сервера.
- Документировать восстановление и **один раз протестировать** его на копии данных.
- Перед потенциально разрушающими изменениями структуры БД — делать резервную копию.
- Можно добавить удобную CLI-команду экспорта оценок позже, но не делать полноценную систему импорта/экспорта через UI в MVP.

## 8. Безопасность и приватность

В `.gitignore` как минимум: `.env*` (кроме `.env.example`), `data/`, `*.sqlite*`, экспортированные CSV и архивы/бэкапы. Не включать личные таблицы в ZIP с документацией или репозиторий. Если использование происходит только в доверенной сети, логин для MVP необязателен; это **не означает, что приложение безопасно публиковать в интернет**.

Не вставлять пользовательские отзывы/метаданные как системные инструкции модели. Ввод пользователя, TMDB и результат LLM — данные, которые нужно ограничивать и валидировать.

## 9. Обогащение TMDB (подфаза 1.4)

Используется API v3 через стандартный fetch, поиск и метаданные — `en-US`. `TMDB_API_KEY` — API key v3 из серверного окружения/.env.local; API Read Access Token не используется этой конфигурацией. При отсутствии ключа CLI завершается до открытия/изменения базы. URL с ключом и сырые сетевые ошибки не выводятся в отчёты.

```sh
npm run tmdb:enrich -- --dry-run --limit 10
npm run tmdb:enrich -- --limit 10
npm run tmdb:enrich
npm run tmdb:enrich -- --retry-unresolved
```

Dry-run делает HTTP-запросы и сохраняет локальный отчёт, но открывает базу readonly и не применяет миграцию. Он работает и на схеме 2. Обычный запуск сначала создаёт SQLite backup в data/backups, затем применяет миграцию №3; отказ backup предотвращает любые изменения. Результат каждого произведения сохраняется отдельной короткой IMMEDIATE-транзакцией. Исходные title/release_year/Letterboxd URI, user_movies, рекомендации и профиль не изменяются.

Автоматическое соответствие требует точного года и нормализованного title либо original_title и повторной проверки подробного ответа. Нормализация сохраняет слова/акценты, учитывает Unicode, регистр, пробелы, кавычки/пунктуацию; нечёткий поиск и популярность не используются. Поиск обходит максимум пять страниц, неполная выдача считается неоднозначной. Несколько подходящих ID, занятый другой записью ID, отсутствующий год и расхождение details требуют ручной проверки. Поиск только movie; неизвестные записи не превращаются в tv автоматически. Известные tv пропускаются. Короткий метр обогащается, runtime 0 хранится как NULL.

Details запрашивается с append_to_response=credits. Сохраняются подтверждённые названия, год, описание, жанры, длительность, постер, язык, рейтинг, голоса, популярность; directors_json — все режиссёры, credits_json — первые 10 актёров по order и crew с ролями Director/Writer/Screenplay/Story/Producer/Executive Producer. Отсутствующие поля — NULL, подтверждённые пустые списки — []; числа/ID/JSON и типы проверяются. Отсутствие отдельного поля не запускает бесконечные повторные запросы после успешной обработки.

По умолчанию обрабатываются pending/error и известные ID с незавершённым обогащением. matched пропускаются; not_found/ambiguous повторяются только с --retry-unresolved. Число записей ограничивает положительный --limit; порядок — локальный id. Статусы сохраняют прогресс при остановке, очереди/фоновые сервисы отсутствуют.

HTTP-запросы идут последовательно с интервалом не менее 250 мс, тайм-аутом 10 секунд и максимум тремя попытками при сети/тайм-ауте/429/5xx. Повторные задержки 1/2 секунды учитывают Retry-After (секунды либо HTTP-дата); пауза свыше 60 секунд и 401/403 останавливают запуск, сохраняя обработанный прогресс. Технические ошибки дают ненулевой exit code; not_found/ambiguous — обычные результаты, не ошибки API.

Отчёты data/tmdb-reports/*.json обновляются после каждой записи через временный файл и rename. В них есть dryRun, число обработанных/сопоставленных/нерешённых/ошибок, HTTP-запросы/неудачные запросы, фактический остаток без ID и кандидаты/причины для ручной проверки. При dry-run matched означает предложенные совпадения; remainingWithoutId отражает неизменённую реальную базу. В штатном CLI подтверждённые записи записываются в SQLite; окончательная проверка полных подборок/рекомендаций относится к следующим фазам.

На 2026-10-25 ключ настроен только локально, live-приёмка выполнена: dry-run 10/10, затем запись выборки и полный проход. ## HTTP-подборки Cinema Spotlight — 4.2

Миграция 5 добавляет nullable `movies.backdrop_path`. Поддерживаемые HTTP-схемы — 3/4/5; чтение ничего не мигрирует. Явная запись после backup доводит базу до актуальной схемы. Пути изображений валидируются и разрешаются только на image.tmdb.org с размерами w342/w500/w1280. Они получены тем же details с credits, не входят в AI-контекст; старые JSON кандидатов без изображений допустимы.

`recommendation-batches.ts` читает согласованный SQLite-снимок: последняя полноценная группа UUID/legacy по времени и ID, порядок вставки внутри группы. Ручные/NULL result_id, неполные объяснения и посторонние идентификаторы не изображают AI-генерацию. После выбора группы применяются актуальные исключения; полностью исчерпанная группа остаётся пустой. Cooldown не применяется к чтению. Для legacy время генерации неизвестно (`generated_at=null`, `time_kind=recorded`).

`recommendation-service.ts` соединяет существующие функции, не держит SQL-транзакцию во время HTTP. GET и предварительные проверки read-only. Подтверждённый POST: lock → backup → миграции → durable journal → кандидаты → ранжирование → durable prepared output → транзакционная запись. Технический partial кандидатов останавливает конвейер до второго запроса. При записи повторно проверяются просмотры, скрытия, cooldown и оценки свидетельств. Возвращаются только сохранённые строки.

Журнал размещён рядом с постоянной базой в `.recommendation-runs/<hash canonical database path>/`, lock — `<canonical database path>.recommendations.lock`. Атомарная замена с fsync, приватные права, UUID-запросы; готовый результат переживает перезапуск. Хранятся результаты/usage и этапы, но не исходные запросы, профиль или reasoning. Каталог и lock должны оставаться вместе с постоянными данными при дальнейшем развёртывании. Это не очередь и не фоновый сервис.

SQL-only восстановление: тот же подтверждённый request_id на `?save_only=1`; при отсутствии журнала — 409 без внешних вызовов. Подготовленный результат проходит текущую валидацию после нового backup. Сохранённый request_id воспроизводится без оплаты; неопределённый запрос не повторяется автоматически. Зависший lock не удаляется автоматически: сначала владелец проверяет PID/процесс. Самостоятельные CLI используют свои прежние правила и не участвуют в HTTP-lock.

Общий предел сетевой операции — 900 секунд с отменой fetch и ожиданий; lock освобождается после фактического завершения, не через ранний Promise.race. Отключение браузера не отменяет подтверждённый запрос в живом процессе. HTTP-ответы no-store, Origin проверяется до JSON/SQLite, внутренние ошибки/ключи/пути наружу не выходят. Приложение по-прежнему предназначено только для доверенной домашней сети.

## Персональные рецензии — схема 6

Миграция `006_movie_reviews.sql` добавляет nullable `user_movies.review_text` с CHECK и отдельный trigger обновления `updated_at` при фактическом изменении текста. Исходные поля Letterboxd и оценка не затрагиваются. Все HTTP-операции поддерживают схемы 3–6; старые записи читаются с `review_text=null` без миграции.

`PATCH /api/library/:id/review` принимает ровно `{ "review_text": "исходный текст" }` либо `null`; пустая/пробельная строка очищает поле. Нужен подтверждённый просмотр. Сервер проверяет тип, длину (2000 UTF-16 code units, как HTML maxlength) и запрещает NUL. Пробелы/переносы непустого текста сохраняются. Ответ `{status,movie_id,review_text}`; ошибки используют существующие Origin/no-store/безопасные коды. `POST /api/movies/:id/watch` дополнительно принимает необязательный `review_text`, атомарно с первой оценкой/просмотром. Пропуск поля сохраняет существующую рецензию; маршрут оценок её не изменяет.

Только эти два маршрута допускают до 24 КиБ JSON, включая Unicode/JSON escaping. Остальные сохраняют 1 КиБ. Backup выполняется до миграции, затем короткая IMMEDIATE-транзакция повторяет проверку просмотра. No-op не меняет timestamps и не создаёт backup. Чтение, старт приложения и health не применяют миграции. Никаких изменений реальной базы или деплоя при реализации не выполнялось.
