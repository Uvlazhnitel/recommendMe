# AGENTS.md — обязательные правила работы Codex

## Перед каждой задачей

1. Прочитай `PROJECT_SPEC.md`, текущую фазу `IMPLEMENTATION_PLAN.md`, соответствующий технический документ и `PROGRESS.md`.
2. Выполняй **только запрошенную фазу или конкретную задачу**. Не начинай следующую фазу без разрешения владельца.
3. Предпочитай **самое простое работающее решение**. Если можно обойтись несколькими функциями, не строй фреймворк вокруг них.
4. При конфликте документов последние явные указания владельца важнее. Запиши принятое изменение в `PROGRESS.md`, при необходимости поправь спецификацию.

## Неизменные цели MVP

- Приложение **только для одного человека**, развёртывание на домашнем сервере, использование на ПК и телефоне.
- Только **полнометражные фильмы** в рекомендациях, не сериалы/короткометражки.
- Один технический импорт `ratings.csv` + `watched.csv` в SQLite. **Не делать загрузку ZIP/CSV через UI, экран импорта, синхронизацию Letterboxd.**
- После импорта — ручное добавление просмотров и оценок **0–100**; все изменения сохраняются.
- Цель — персональные рекомендации уровня качественного ChatGPT-анализа истории оценок, а не банальный TMDB-поиск/сортировка по популярности.
- Исключать **всё уже просмотренное**, включая просмотренное без оценки. Отсутствующая оценка `NULL` **не** равна оценке `0`.
- Допускать малоизвестное кино при убедительном соответствии вкусу; не выдавать случайные малоизвестные/низкоинформативные находки.
- Оценки и отклонения имеют разный смысл: «неинтересно» скрывает рекомендацию, но не ставит фильму ноль.
- Не показывать придуманные «вероятность 94%», «точность модели 97%» или якобы измеренные показатели.

## Архитектурные запреты до отдельного решения

**В MVP не нужны:** FastAPI, отдельный Python backend, Python ML-сервис, MovieLens/bir.mov, LensKit, embeddings/векторная БД, обучаемая нейросеть, RAG-платформа, Redis, очереди, Kubernetes, OAuth, соцфункции, платёжная система, мобильные native-приложения, микросервисы, сложная дизайн-система.

Базовый стек: **Next.js + TypeScript + SQLite + TMDB API + LLM API + Docker Compose**. Один репозиторий, одно приложение, одна база. Для SQLite достаточно лёгкого SQL-слоя; не вводи ORM или дополнительные сервисы, если они не решают конкретную проблему.

Если возникает реальная причина нарушить ограничение, сначала изложи проблему и **минимальную альтернативу**, а не внедряй новую технологию молча.

## Как обращаться с рекомендациями

- Следуй конвейеру из `RECOMMENDER.md`: сохранённый профиль вкуса + новые оценки → предложения LLM и TMDB → проверка реальности, формата и просмотров → окончательный LLM-отбор по списку допустимых ID.
- Проверяй TMDB ID, тип `movie`, длительность; не доверяй названиям и фактам, придуманным LLM.
- Учитывай положительные **и отрицательные** оценки, а также контрастные пары; не своди вкус к жанрам.
- Новая/изменённая оценка должна учитываться **в следующем запросе**, даже если большой профиль вкуса ещё не пересчитан.
- Не отправляй весь исходный CSV в каждый LLM-запрос. Кешируй профиль и метаданные, ограничивай размеры запросов и логируй расход токенов, если провайдер его возвращает.
- При ошибке API объясняй проблему, не выдавай вымышленные рекомендации. Допустимо показать меньше пяти фильмов.

## Защита данных и домашнего сервера

- Не коммить личные CSV, SQLite-файлы, бэкапы, `.env` и API-ключи. Создай корректный `.gitignore`.
- LLM/TMDB API-ключи только на серверной стороне. Внешние TMDB-описания и LLM-ответы считать недоверенными; валидировать данные.
- SQLite расположить в постоянной директории, смонтированной в контейнер. Не удалять/перезаписывать историю при пересборке.
- На старте запускать **только в доверенной домашней сети**. Не выставлять приложение с отключённой авторизацией и API-ключами в открытый интернет. Удалённый доступ — отдельное решение позднее.
- Любые миграции/импорт должны быть безопасны для существующих данных, с проверкой и резервной копией там, где нужен рискованный шаг.

## Формат работы и Definition of Done

Перед реализацией коротко скажи: **что делаешь, как проверишь, что сознательно не делаешь**. Затем действуй без лишних теоретических исследований.

После задачи:
1. Проверяй минимальные автоматические тесты и/или воспроизводимый smoke test; не говори «проверено», если не запускал.
2. Сообщи файлы, изменения, фактический результат проверки и известные ограничения.
3. Обнови `PROGRESS.md` (статус, дата, факт выполнения, проблемы, следующий шаг); если изменились требования — обнови нужный `.md`.
4. **Остановись** после текущей задачи. Не добавляй функции «на будущее».

Никакого усложнения ради «масштабируемости» персонального приложения. Главный приоритет — качественные рекомендации, надёжные личные данные и быстро работающий MVP.
