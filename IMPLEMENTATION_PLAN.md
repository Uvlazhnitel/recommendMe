# IMPLEMENTATION_PLAN.md — пять фаз MVP

## Принцип

**Одна фаза = одна законченная проверяемая задача.** Не реализовать всё одновременно. После фазы Codex проверяет результат, обновляет `PROGRESS.md` и останавливается до следующей команды владельца.

Уровень строгости: **надёжные данные + хорошие рекомендации + простой UI**. Не строим production-SaaS и не проводим многонедельные ML-исследования.

## Фаза 1 — фундамент + первоначальное заполнение SQLite

**Цель:** базовое приложение и настоящие пользовательские данные в устойчивом хранилище.

**Сделать:**
- Создать минимальный Next.js + TypeScript проект (один репозиторий, серверные API routes/server actions при необходимости).
- Подключить SQLite с минимальным драйвером и SQL-миграциями. Ввести схему из `DATA_AND_DEPLOYMENT.md`.
- Создать `.gitignore`, `.env.example`, постоянный каталог `./data`. Docker/Compose отнесены к фазе 5 по уточнённым границам подфазы 1.5.
- Создать **локальный backend CLI-скрипт** `seed` для `watched(6).csv` и `ratings(6).csv`; корректно объединить по `Letterboxd URI`, перевести шкалу, сохранить исходные звёзды и просмотренные без оценки.
- Подготовить TMDB-клиент/сопоставление; сомнительные совпадения отмечать для проверки, **не угадывать**. Можно обогащать данные пакетами, не блокируя импорт всей истории.
- Вывести отчёт импорта (сколько добавлено/обновлено, сколько unresolved, сколько просмотрено без оценки).

**Не делать:** рекомендательные промпты, ML, LLM, три полноценных страницы, UI загрузки CSV.

**Готово, если:**
- Next.js стартует локально в dev и production; TypeScript, lint, тесты и сборка проходят.
- Скрипт корректно обрабатывает оба файла; **830 просмотренных, 519 оценённых, 311 без оценки**, до учёта возможных заранее существовавших ручных записей.
- Импорт повторно не создаёт дубликатов и не стирает более свежие ручные оценки.
- Проверены крайние случаи (0 и NULL, UTF-8/названия, год, конфликтующие имена).
- SQLite сохраняется после перезапуска приложения; ключи/CSV/БД игнорируются Git. Перезапуск контейнера проверяется в фазе 5.

### Уточнённые подфазы фазы 1

1. **1.1** — минимальное приложение, подключение SQLite, окружение и health.
2. **1.2** — схема, ограничения и повторяемые SQL-миграции.
3. **1.3** — первоначальный импорт двух CSV и проверка 830/519/311.
4. **1.4** — TMDB, метаданные, консервативное сопоставление и отчёты.
5. **1.5** — сквозная проверка, повторные операции на временной копии, live smoke и готовность данных к фазе 2.

Отсутствие TMDB ID у явно нерешённых записей не блокирует фазу 1 при сохранённой истории и отчёте. Отдельно оценивается покрытие метаданными оценённых фильмов. Docker, OpenAI, рекомендации и UI не входят в подфазу 1.5.

## Фаза 2 — прототип рекомендательного движка (главный приоритет)

**Цель:** получить первые осмысленные рекомендации **без построения UI**.

**Сделать:**
- Сохранить в базе компактный структурированный **профиль вкуса**, построенный из высоких/низких/контрастных оценок и доступных метаданных.
- Подготовить два источника кандидатов: (a) названия от LLM по истории и профилю; (b) релевантные кандидаты из TMDB по любимым фильмам/авторам/темам и общему качеству данных.
- Сопоставить предложенные названия с TMDB, добавить метаданные, исключить просмотренные, отклонённые, несуществующие, дубликаты, сериалы, короткометражки.
- Отобрать до 20–40 пригодных кандидатов; попросить LLM выбрать до пяти **из их ID**, с конкретными аргументами «за»/«против».
- Реализовать серверную/CLI-команду для получения и вывода подборки. Сохранять подборку и расход токенов (если доступен) для анализа.
- Обеспечить учёт изменённой или добавленной оценки в **следующем** вызове: последние изменения отправлять вместе с сохранённым профилем. Сводку обновлять по разумному триггеру (например, 10 изменений) или CLI-командой.
- Сделать минимальные автоматические тесты для жёстких фильтров и ручную проверку **2–3 подборок**. Исправлять очевидные ошибки и случайные obscure-рекомендации.

**Не делать:** обучение ML, embeddings, отдельный Python backend, графическую библиотеку или десятки вариантов промптов.

**Готово, если:**
- Команда выдаёт 1–5 **существующих** полнометражных фильмов с TMDB ID, не просмотренных ранее.
- Рекомендации конкретно объясняются через личный вкус, без общих шаблонов и ложных фактов.
- Дополнительная новая оценка меняет входные данные следующего вызова.
- Неизвестные ID и невалидные ответы LLM не проходят; при API-ошибке понятный отказ без фальшивых результатов.
- Размер контекста ограничен, стоимость/токены по возможности наблюдаемы.

## Фаза 3 — ручные оценки и библиотека (функциональность)

**Цель:** от CSV перейти к регулярному использованию собственной базы.

**Сделать:**
- Реализовать серверные методы для: поиска TMDB, добавления просмотра, назначения/редактирования/очистки оценки 0–100, получения списка библиотеки, отметки «Неинтересно».
- Минимальные формы/страницы с рабочей функцией сохранения (пока без полировки дизайна).
- Гарантировать, что `0` сохраняется как валидная оценка, а «просмотрено без оценки» остаётся `NULL`.
- Интегрировать изменения с рекомендателем из фазы 2.

**Не делать:** расширенную статистику, отзывы и теги, автоматический поиск по стримингам, отдельный аккаунт.

**Готово, если:**
- Ручная оценка сохраняется, обновляется и переживает перезапуск.
- Старая импортированная оценка редактируется без потери идентичности фильма.
- Отмеченный просмотренным фильм исчезает из будущих рекомендаций; «Неинтересно» не меняет оценку/факт просмотра.

## Фаза 4 — удобный адаптивный интерфейс

**Цель:** приложение приятно использовать на смартфоне и ПК.

**Сделать:**
- Три раздела: **Рекомендации**, **Оценить фильм**, **Библиотека**.
- Карточки с постерами TMDB, названием, годом, длительностью, обоснованием и рисками; действия «Ещё», «Неинтересно», «Посмотрел/оценить».
- Поиск, список, редактирование и шкалу 0–100; адекватные empty/loading/error states.
- Небольшую мобильную адаптацию без отдельного приложения.

**Не делать:** анимации ради анимации, чат, графики, новую модель рекомендаций.

**Готово, если:** вручную пройден полный сценарий от рекомендации до новой оценки на десктопе и телефоне (или в мобильном эмуляторе).

## Фаза 5 — развёртывание на домашнем сервере и приёмка

**Цель:** стабильно пользоваться приложением самостоятельно.

**Сделать:**
- Создать Dockerfile и минимальный Docker Compose с одним сервисом app; проверить `docker compose up -d --build`, постоянную БД в `./data`, права записи и переменные окружения.
- Проверить доступ в домашней сети с компьютера и телефона. **Не** открывать сервис в публичный интернет без отдельной защиты.
- Описать и проверить восстановление SQLite из резервной копии; перед рискованными миграциями — backup.
- Проверить отсутствие секретов/личных CSV в Git; серверные API-ключи не попадают в браузер.
- Сделать небольшие ручные тесты рекомендаций, повторов, исключений и обновления после новых оценок.
- Обновить инструкции README фактическими командами, если они отличаются от первоначальных предположений.

**Готово, если:** приложение проходит сценарии `PROJECT_SPEC.md` и реально работает на домашнем сервере без потери данных.
