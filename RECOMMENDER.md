# RECOMMENDER.md — рекомендательная система MVP

## Главная установка

Наша задача — воспроизвести сильные стороны рекомендации ChatGPT, когда он анализирует **всю историю личных оценок**: понимать контрастные предпочтения, не подменять вкус популярностью и выбирать реальные хорошие фильмы. Это **не** поиск любых похожих названий по TMDB и **не** сортировка по IMDb/TMDB score.

Нет обучения собственной ML-модели в MVP. Под «обучением на новых оценках» понимаем, что сохранённая история участвует в очередной генерации и периодически обновляет вкусовой профиль.

## 1. Создание вкусового профиля

**Когда:** в подфазе 2.1 — только по явному CLI-запуску с --live; повторная генерация существующего профиля — только с --force. Автоматический триггер по накоплению изменений (ориентир: 10 оценок) относится к последующим подфазам и сейчас не реализован.

**Вход:**
- История 519 оценок (с учётом новых записей), её распределение и выбранные показательные фильмы.
- Высокие, средние и низкие оценки; контрастные пары в похожих жанрах/сериях/темах.
- Подтверждённые метаданные по доступным фильмам (не придумывать неизвестные факты).
- Просмотренные без оценки **не используются как отрицательные сигналы**.

**Структурированный результат (JSON или типизированный объект):**
- `strong_preferences`: что регулярно совпадает с высокой оценкой, с примерами.
- `negative_patterns`: что чаще снижает личную оценку, с примерами.
- `contrasts`: пары похожих фильмов с разными оценками — **без выдуманных причин**.
- `uncertainties`: какие выводы слишком слабо подтверждены.
- `profile_version`, `generated_at`, `ratings_count` — техническая метаинформация.

Не сводить профиль к «любит фантастику / не любит хорроры»; избегать утверждений о психологических причинах без наблюдаемых данных.

**Экономия:** профиль сохраняется в SQLite. Повторное создание при каждом запросе запрещено; изменения после профиля отправляются отдельным компактным списком оценок. Если пользователь изменил оценку давно оценённого фильма, тоже учитывать изменение, а не только дату просмотра.

### Реализованный контракт подфазы 2.1

- Контекст: все rating_100 IS NOT NULL (включая 0 и записи без TMDB ID), локальный ID/название/год/оценка и статистика. NULL-просмотры не передаются как отрицательные сигналы. Богатые примеры берутся только из подтверждённых TMDB-метаданных.
- До 20 подробных примеров в каждой группе high ≥80, medium 61–79, low ≤60: round-robin по встречающимся оценкам, затем максимизация ещё не представленных режиссёров/жанров (новый режиссёр весит 3, жанр — 1), tie-break по локальному ID.
- До 12 контрастов: разница ≥20, общий режиссёр либо минимум два общих жанра. Сортировка — наличие общего режиссёра, Jaccard общих жанров, разница оценок, ID. Фильм используется максимум в двух входных парах. Общность метаданных не объявляется причиной оценки.
- Лимит сериализованных input + text.format/schema — 120 000 UTF-8 байт. Сначала обрезаются описания 600→300→150→0 символов, затем симметрично сокращается число примеров на группу, затем дополнительные пары; все базовые оценки остаются. Невместимый обязательный набор прекращает запрос, не отбрасывая группы.
- Промпт английский; внешние описания передаются как недоверенный пользовательский JSON, отдельно от системных требований. Запрещены рекомендации, вымышленные факты/психология/точные вероятности и внешние URL. Свободные объяснения требуют человеческой оценки; структурная проверка не доказывает истинность каждого вывода.
- Выход модели: strong_preferences/negative_patterns с summary, explanation, kind (observation/hypothesis), uncertainty, evidence [{movie_id,rating_100}]; contrasts с higher/lower evidence, similarity, possible_difference, uncertainty; uncertainties с description/evidence. Структура ограничена JSON Schema без лишних полей, длины/число элементов ограничены. Проверяются реальные ID/оценки из снимка, отсутствие повторов свидетельств/пар и разница ≥20; позитивные/негативные разделы требуют соответствующих high/low свидетельств. При входных парах требуется контраст. Полностью пустой анализ не сохраняется.
- Приложение добавляет profile_version, generated_at, ratings_count, ratings_snapshot, context_fingerprint, prompt_version/schema_version, contrast_pairs_count, requested_model/model, response_id и usage. Минимальный снимок ID/оценок хранится в приватной БД для проверки исторического профиля; полный TMDB-контекст и reasoning не сохраняются. Таблица taste_profile не расширяется.
- SHA-256 охватывает канонические входные сообщения, схему и версии; изменение оценки учитывается даже при прежнем количестве записей. Валидный кеш возвращается без API, устаревание не запускает платную перегенерацию. При очищении всех оценок прежний профиль остаётся доступным как stale.
- --live требует OPENAI_API_KEY и явного OPENAI_MODEL, использует один Responses-запрос, strict JSON Schema, store:false, max_output_tokens=12000 и тайм-аут 180 секунд. Автоматических повторов и переключения модели нет. Предполагаемый начальный модельный ID — gpt-6.1-sol, доступ аккаунта не проверен. Ошибки/отказ/incomplete не уничтожают старый профиль; сохраняются только доступные input/output tokens, без выдуманной стоимости.
- Live-запуск использует эксклюзивный lock с PID рядом с SQLite и backup до API. После получения lock кеш проверяется ещё раз. До атомарного UPSERT проверяются отпечаток актуального контекста и неизменность предыдущего профиля; HTTP не выполняется внутри SQL-транзакции. Lock освобождается в finally. Восстановление после аварии — проверить PID и вручную удалить только подтверждённо устаревший lock.
- Команды: `npm run taste:generate -- --dry-run` (также режим по умолчанию), `--live`, `--live --force`, `npm run taste:show`. Show получает названия из SQLite, показывает оценку на момент генерации и отдельно изменившуюся текущую оценку; новые имена/URL из модели не создаются.

На этапе реализации 2.1 выполняются только dry-run и мок-тесты; даже настроенный ключ не является поручением автоматически тратить токены. **Реальный профиль и его содержательное качество пока не проверены.**

## 2. Поиск кандидатов: два направления

### А. Предложения LLM — главный источник «как ChatGPT»

Передать профиль + подобранные из истории примеры 4–5★, 0–3,5★ и недавние изменения. Попросить **примерно 20–30** разных полнометражных фильмов, которые могли бы понравиться, с названием и годом. Модель пока предлагает гипотезы, **не** создаёт записи в основной базе как подтверждённые фильмы.

Формат ответа — машиночитаемый JSON. Ограничить число кандидатов. Один основной LLM-запрос без автоматического исправления или повтора. Невалидный ответ, refusal или incomplete дают понятную ошибку, без подмены подборкой одного TMDB.

### Б. TMDB — дополняющий источник

Подобрать ещё несколько десятков кандидатов из связанных фильмов, авторов, жанров/тем и в разумной мере общепризнанных фильмов. Не брать просто «топ по популярности», не доверять одному similarity endpoint как финальной рекомендации. Смешивать кандидатов до итогового отбора и удалять дубликаты.

**Внимание:** отсутствие достаточных метаданных, низкий vote_count и низкая популярность — признаки *неопределённости*, а не доказательство плохого качества. Никакого универсального запрета на малоизвестное кино. Но у совсем obscure фильма должно быть содержательное обоснование.

### Реализованный контракт подфазы 2.2

- `npm run candidates:generate` / `--dry-run`: read-only SQLite, проверка сохранённого профиля, настроек, истории, размеров и лимитов; внешних вызовов нет. Нет профиля или он повреждён — код 1 до API, автоматической генерации профиля нет. `--live` запускается только владельцем явно; несовместим с --dry-run.
- Сохранённые смысловые разделы профиля + реальные имена свидетельств из SQLite, до 10 high/10 low примеров и 6 контрастов из существующего отбора. Все новые/изменённые/очищенные оценки вычисляются сравнением текущей истории и ratings_snapshot; текущие значения приоритетнее старых выводов. Устаревший профиль не пересоздаётся.
- Английский промпт требует разнообразия и учёта негативных/противоречивых сигналов, запрещает случайные obscure-находки и финальное ранжирование. Недоверенные данные — отдельный user JSON. Лимит input + schema 120 000 UTF-8 байт: описания → необязательные примеры → контрасты → компактные исключения; профиль и изменения оценок остаются обязательными.
- LLM: strict schema `{candidates:[{title,year}]}`, максимум 30. Общий с 2.1 Responses-транспорт, модель только из OPENAI_MODEL, store:false, max_output_tokens=12000, 180 секунд, один запрос без повтора/смены модели. Usage выводится при наличии; reasoning не выводится. Ошибка OpenAI прекращает генерацию без TMDB-only fallback.
- TMDB: существующий клиент дополнен `/movie/{id}/recommendations`, только первая страница для до пяти high≥80, movie, runtime≥60, известных ID без not_interested. Выбор максимизирует новые режиссёры/жанры (3/1), затем оценку и ID. До 25 разных предложений обходом страниц по очереди, без сортировки по популярности.
- LLM-гипотезы: точный год и нормализованное совпадение с title/original_title, полная проверка выдачи до пяти страниц. Несколько совпадений или неполная выдача — пропуск. Для каждого нового ID — movie details с credits и повторная проверка личности. Только movie, runtime≥60, известный год, непустое описание и жанры. Режиссёр/число голосов/популярность могут быть NULL; минимального порога популярности нет.
- Просмотренные и not_interested исключаются по ID; записи без ID — по нормализованным title/tmdb_title/original_title и исходному году (TMDB-год используется только при неизвестном исходном). При неизвестном годе совпадение названия пропускается как uncertain_history_match. NULL-оценка не мешает исключению просмотра. Перед выдачей состояния читаются повторно. recommendations.rejected отдельно не превращается в глобальный запрет.
- Не более 55 details-проверок и 120 фактических TMDB HTTP-попыток, включая retries. Последовательность, интервал ≥250 мс, timeout 10 секунд и существующие 429/5xx/network retries сохраняются. Поиски/details кешируются на запуск. API-ошибки, авторизация, превышение бюджета дают ненулевой код; частичный результат явно помечается partial, без выдуманного дополнения.
- До 40 уникальных MovieCandidate: tmdb_id/media_type=movie/title/original_title/year/overview/genres/runtime/directors/vote_count/popularity/source (llm/tmdb/both). Метаданные только проверенные TMDB, порядок LLM → TMDB без оценки качества; меньше 20 допустимо. Никаких записей фильмов/профиля/рекомендаций, миграций или новых HTTP-маршрутов.
- Подфаза проверяется на временных БД и HTTP-моках. В рабочей БД профиль пока отсутствует: реальный запуск и содержательное качество кандидатов не проверены. Финальный отбор реализован отдельно в подфазе 2.3; его live-приёмка также ожидает профиля и кандидатов.

## 3. Подтверждение фильма и жёсткие фильтры

Каждый предложенный фильм:
1. Разрешить через TMDB поиск по названию/году; при нескольких правдоподобных совпадениях выбрать только после проверки или пропустить.
2. Получить **реальный `tmdb_id`** и достаточные метаданные.
3. Допустить **только `movie`**, не `tv`. Для MVP считать полнометражным `runtime >= 60` минут; если длительность неизвестна, не включать в автоматическую выдачу до уточнения.
4. Исключить **всю** просмотренную историю — в том числе 311 старых без оценки — и фильмы, недавно вручную добавленные как просмотренные.
5. Исключить `not_interested`/скрытые, а также дубликаты в подборке.
6. Избегать повторного навязывания ранее показанных карточек; можно учитывать журнал рекомендаций, но не превращать каждую выдачу в необратимый запрет всех ранее предложенных фильмов.
7. Если у старой записи нет TMDB ID, дополнительно сравнить нормализованные `title + year`, чтобы не предложить просмотренный фильм под другим ID.

Фильмы из списка, не прошедшие валидацию, **не показывать**. Если осталось менее пяти — показать меньше либо расширить поиск, но не выдумывать кандидатов.

## 4. Финальный LLM-отбор — подфаза 2.3

**Запуск:** `npm run recommendations:rank -- --input data/candidates.json --dry-run` (также по умолчанию); платный запрос только с --live. Профиль и кандидаты должны быть созданы отдельно; ранжирование их не генерирует. SQLite всегда read-only, TMDB не вызывается, история рекомендаций не сохраняется. --input обязателен, --dry-run/--live несовместимы.

**Вход:** сохранённый вывод 2.2 с mode=live/status=ok или partial и максимум 40 уникальными кандидатами. Для JSON перенаправлять `npm run --silent candidates:generate -- --live > data/candidates.json`; обычный npm-заголовок делает файл невалидным. Partial принимается с предупреждением. MovieCandidate теперь включает media_type=movie; отсутствие маркера требует нового вывода 2.2. Это локальный артефакт предварительной проверки: поля валидируются, но метаданные повторно через сеть не подтверждаются.

До запроса отбрасываются невалидные поля, TV, runtime<60/неизвестная длительность, просмотренное и not_interested. Повторные входные ID, более 40 записей и повреждённый JSON — ошибка до API. Фильтр просмотра/скрытия переиспользован из 2.2: TMDB ID либо нормализованные названия/год для истории без ID, с безопасным пропуском неизвестного года. Малоизвестный фильм не запрещается по числу голосов или популярности.

**Контекст:** общая с 2.2 подготовка сохранённого профиля, реальных имён свидетельств, текущих оценок и всех отличий от ratings_snapshot, включая новые/изменённые/очищенные оценки. До 10 high/10 low примеров и 6 контрастов из существующего отбора; до 10 дополнительных связанных примеров из подтверждённых метаданных всей оценённой истории — общий режиссёр, затем число общих жанров, затем ID. Повторов с основной выборкой нет. 0 — реальная оценка; NULL не отрицательный сигнал. Устаревший профиль не пересоздаётся, текущая история приоритетнее старых выводов. Отдельный current_evidence содержит только действительно переданные текущие ID/названия/годы/оценки, включая записи без TMDB ID.

Лимит input + schema — 120 000 UTF-8 байт: описания кандидатов 1200→600→300→0, затем примеров 600→300→150→0, связанные примеры, симметрично high/low-примеры, дополнительные контрасты. Профиль, все дельты и основные поля всех допустимых кандидатов остаются. Обязательное переполнение или отсутствие текущих оценённых свидетельств прекращает запуск до API. Dry-run показывает размер, количество примеров/кандидатов/дельт, готовность настроек и неточную оценку токенов, не выводит приватный полный контекст.

**LLM:** существующий requestStructuredOutput, OPENAI_MODEL без автоматической смены, один Responses-запрос, strict JSON Schema с enum допустимых TMDB ID и additionalProperties=false, store:false, 180 секунд и max_output_tokens=12000. Никаких повторов, исправляющих запросов или TMDB-only fallback. Английский промпт требует персонального сравнения положительных и отрицательных закономерностей, контрпримеров и контрастов; причинные объяснения — гипотезы. Запрещены вымышленные факты, психологические причины, точные вероятности и неоправданное предпочтение популярности. Профиль/метаданные — отдельный недоверенный user JSON.

**Ответ модели:**

```ts
{
  recommendations: Array<{
    tmdb_id: number;
    why_fit: string;
    possible_mismatch: string;
    evidence: Array<{ movie_id: number; rating_100: number }>;
  }>;
}
```

От 1 до 5 элементов, порядок массива — ранжирование. why_fit непустой, до 1000 символов; possible_mismatch — до 600, с конкретным подтверждённым риском либо честной неопределённостью. На элемент 1–6 уникальных ссылок на current_evidence с точными оценками. Эти ссылки могут поддерживать аргумент соответствия и/или риска. Фиктивные match_percentage/predicted_rating/confidence_score и другие дополнительные поля запрещены.

**Серверная проверка:** структура, положительные целочисленные ID, исходный разрешённый набор, дубли, тексты и свидетельства. Чужие/невалидные элементы исключаются с причинами; первый валидный экземпляр ID сохраняется, порядок не меняется. Прямо перед возвратом одним новым SQL-снимком повторно проверяются просмотр/скрытие и текущие оценки свидетельств; изменённая/очищенная оценка исключает соответствующую рекомендацию. Тип movie/runtime≥60 проверяются по загруженным подтверждённым данным. Названия/годы кандидатов берутся из входа, свидетельств — из SQLite, не из ответа модели.

Корректные 1–5 результатов возвращаются без дополнения до пяти, с диагностикой исключений, моделью и доступным фактическим usage. Ноль валидных результатов, отказ, incomplete, невалидный корень/JSON или API-ошибка — понятная ошибка и код 1, без случайной подстановки. Личные таблицы и timestamps не изменяются. Проверка ссылок подтверждает реальные фильмы и оценки, но не является автоматической проверкой всех свободных фактов или художественного качества текста.

**Приёмка:** локальные тесты с временными БД/HTTP-моками и dry-run; платный запуск не выполнялся. В рабочей БД профиль пуст и реального файла кандидатов нет. Содержательное качество и фактический live usage пока не проверены. История рекомендаций относится к 2.4 и не реализована.

## 5. После ручной оценки

- Сохранить просмотр/оценку в SQLite **до** AI-вызовов.
- Из следующей подборки фильм уже исключён.
- При формировании очередного запроса прочитать **актуальную** историю и отличающиеся после профиля оценки. Никакой fine-tuning не нужен.
- После условных 10 изменённых/добавленных оценок профиль можно пересоздать; сначала это простой синхронный/CLI-механизм, а не очередь и не сложный background worker.
- «Неинтересно» исключает фильм, **но не является оценкой 0/100** и не идёт в профиль как негативный отзыв о качестве.

## 6. Защита от плохих рекомендаций

- **Точность идентификации:** `tmdb_id`, год, длительность, тип.
- **Контроль крайностей:** если редкий фильм выбран только на основе похожего описания без достаточного подтверждения — отодвинуть его в пользу более обоснованного; популярность сама по себе не решает.
- **Качество аргумента:** рекомендации должны объяснять соответствие **конкретному** вкусу, включая контрасты.
- **Лёгкая проверка:** 2–3 подборки при разработке, реальные отклики владельца, запись заметных ошибок в `PROGRESS.md`. Не объявлять алгоритм точным без данных.
- **Работа без API:** если сервис недоступен, честная ошибка и сохранённая история; не подставлять случайные фильмы из TMDB.

## 7. Контроль стоимости

- Модель и провайдер LLM **настраиваемые через серверные переменные окружения**. Не фиксировать конкретную дорогую модель и не предполагать неизменность цен API.
- Не отправлять полный CSV в каждом запросе; передавать профиль, выборочные примеры, новые оценки и ограниченный список кандидатов.
- Кешировать TMDB-метаданные и профиль.
- Поставить ограничения на количество предлагаемых/передаваемых фильмов и повторных LLM-попыток.
- Если API возвращает usage, хранить `input_tokens`/`output_tokens`/модель; доллары вычислять лишь по **проверенному актуальному тарифу** (можно вручную).
- Не добавлять коммерческие мониторинги, ML-пайплайны, агентные циклы и дополнительные нейросети в MVP.

## 8. Что тестировать в первую очередь

- LLM предложила название, которого нет в TMDB: **отбросить**.
- LLM вернула не входящий `tmdb_id`: **отбросить**.
- Фильм уже просмотрен без оценки: **отбросить**.
- Фильм уже получил ручную оценку: **отбросить**.
- Фильм помечен «Неинтересно»: **отбросить**, оценку не изменять.
- Тот же фильм пришёл двумя источниками/названиями: **одна карточка**.
- Сериал или короткий метр: **отбросить**.
- Малоизвестный, но действительно релевантный фильм: **допустим**, если хватает фактов для обоснования.
- Новая оценка сохранена: следующий запрос учитывает её, даже если профиль устарел.

**Только после MVP**, если качество реально недостаточно: проверка на скрытых оценках, embeddings, MovieLens/bir.mov и персональные ML-модели — как отдельные эксперименты, не обязательные зависимости.
