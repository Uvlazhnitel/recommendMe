# Personal Movie Recommender

Личное веб-приложение для рекомендаций полнометражного кино по истории оценок владельца. Цель будущего рекомендателя — находить фильмы с личной оценкой 80/100 и выше; это не гарантия результата.

## Evaluation v1 — локальная реализация 2026-10-28

Офлайн-отчёт собирает реально сохранённые AI-подборки, известные версии и фактический OpenAI usage. Качество определяется только подтверждёнными событиями приложения: рекомендация → подтверждение просмотра → назначение оценки. Один фильм относится к последней сохранённой рекомендации перед просмотром; используется текущая оценка, очистка до NULL делает результат неизвестным. Непросмотренные фильмы не считаются неудачами, старые оценки не превращаются в результаты рекомендаций.

```sh
npm run evaluation:report
npm run --silent evaluation:report -- --json
npm run evaluation:report -- --from 2026-10-01 --to 2026-10-31
# Для отдельного существующего readonly снимка:
DATABASE_PATH=/absolute/path/to/snapshot.sqlite npm run --silent evaluation:report -- --json
```

CLI запускается из checkout с установленными dev dependencies (`tsx`), по правилам остальных локальных CLI. В минимальном Docker runtime dev dependencies отсутствуют: для отчёта использовать такой checkout и согласованный приватный снимок либо окружение с Node и зависимостями; новый экран/сервер аналитики не добавлен. Отчёт не создаёт БД и не мигрирует её. Период — сохранённые подборки в UTC (последняя дата включительно), оценки — текущие на момент чтения. При менее20 наблюдений показываются числа и `insufficient_data`;20 не означает статистической надёжности.

Миграция7 добавляет две компактные таблицы. Для новых подборок версии и usage записываются атомарно с рекомендациями, без дубликатов на replay/save_only. Историческая версия остаётся unknown; достоверный исторический usage можно прочитать из однозначного journal. Поля cache/reasoning являются частью input/output и не прибавляются повторно; отсутствующие поля неизвестны, долларов нет. Пример ниже **синтетический**, не качество рабочей системы:

```text
Saved batches: 2; recommendations: 2
Observed: 1/2; unobserved: 1
Hit rate 80+: 1/1 (100.0%)
Mean: 90; median: 90
Status: insufficient_data
```

На доступном readonly-снимке реального аудита:2 подборки/10 рекомендаций,0 достоверных последующих оценок, версии unknown. Рабочие данные не мигрировались; реализация Evaluation не развёрнута. Методика — [RECOMMENDER.md](RECOMMENDER.md#evaluation-v1--2026-10-28), хранение — [DATA_AND_DEPLOYMENT.md](DATA_AND_DEPLOYMENT.md#evaluation--схема-7), проверки/полный список файлов — [PROGRESS.md](PROGRESS.md#evaluation-v1--2026-10-28).

## Candidates v2 — локальная реализация 2026-10-28

В `feature/candidates-v2` подготовлены детерминированная ротация максимум пяти TMDB seeds по числу сохранённых подборок и локальный greedy-отбор максимум 40 проверенных кандидатов. Seeds учитывают актуальные положительные evidence профиля, пересечения жанров/режиссёров и окно оценок 10 баллов. После финального аудита кандидаты сначала получают представителя каждого ещё не покрытого точного набора ID режиссёров/жанров, затем сравниваются по поддержке подтверждённой историей, доступным данным о режиссёре, избыточности и слабому tie-break `both`; `llm` и `tmdb` равноправны. Контрпримеры не создают штрафа. Новых полей в LLM-запросах, миграций или дополнительных API-вызовов нет.

На синтетическом примере 24 LLM +20 TMDB прежний source-order исключал TMDB2016–2019, опубликованный v2 — LLM1020–1023, после аудита —1019/1021–1023: необычный1020 получает шанс вместо ещё одного точного повтора. Состав20/20 не является квотой: контрольный случай сохраняет24 различающихся поддержанных LLM. **285/285 тестов**, lint/typecheck/build и diff --check прошли; полный мок-прогон сохраняет2 OpenAI +73 TMDB. Полные запросы candidates:6428→6428, ranking опубликованный v2→аудит:49821→49791 байт. При одинаковых упорядоченных входах контексты прежние.

Реальное улучшение качества не измерено. Защита относится к точным наборам метаданных и не гарантирует включения каждого необычного фильма. На homeserver остаётся образ `recommendme:candidates-v2-9d29247`; исправление аудита **не развёрнуто**. Алгоритмы и результаты — [RECOMMENDER.md](RECOMMENDER.md#финальный-аудит--2026-10-28), журнал — [PROGRESS.md](PROGRESS.md#финальный-аудит-recommendme-20--2026-10-28).

## Taste Context v2 — 2026-10-28

Обычный подбор использует отдельный детерминированный отбор до 10 высоких и 10 низких примеров, а затем до 10 дополнительных свидетельств для всего набора кандидатов. Учитываются разные стороны сохранённого профиля, контрасты, покрытие кандидатов и повторы; средняя оценка может стать контрпримером. Рецензия служит дополнительным признаком информативности при равных основных условиях.

Ручной полный профиль и его fingerprint не менялись; перегенерация для нового контекста не нужна. Те же два OpenAI-вызова, модель из конфигурации, JSON Schema, TMDB seeds и лимиты. Сходство темы/декораций не объявляется сильным доказательством вкуса. Реализация локальная, в `feature/taste-context-v2`, без деплоя или live API-проверок. Алгоритм, synthetic before/after и ограничения — [RECOMMENDER.md](RECOMMENDER.md#taste-context-v2--2026-10-28); фактические проверки — [PROGRESS.md](PROGRESS.md).

## Личная библиотека — подфаза 4.4

`/library` показывает только просмотренную историю адаптивной сеткой постеров: 2/4/5/6 колонок, по 25 фильмов на страницу. На карточке — название, год и личная оценка 0–100 либо «Без оценки». Короткометражки, импортированные записи без TMDB ID и просмотренные без оценки остаются в коллекции. Отсутствующий постер заменяется нейтральной заглушкой с названием; метаданные автоматически не обновляются.

Поиск применяется по Enter или кнопке, поддерживает исходное, TMDB- и оригинальное названия через существующий API. Доступны наличие оценки, точный год и четыре сортировки: недавно/ранее добавленные и оценка по убыванию/возрастанию. Дата добавления не выдаётся за дату просмотра. Фильтры сбрасывают номер страницы; очистка поиска сохраняет остальные условия, общий сброс возвращает defaults. Общее количество просмотренных и число результатов читаются из SQLite, без фиксированных чисел и загрузки всей коллекции.

Применённые `q`, `rated`, `year`, `sort`, `page` находятся в URL, например `/library?rated=false&sort=rating_desc&page=2`. `movie_id` открывает отдельный экран деталей на телефоне и компьютере. Обновление страницы и Back/Forward сохраняют контекст; возврат восстанавливает позицию и фокус из sessionStorage, если хранилище доступно. После изменения оценки список перечитывается; фильм может переместиться или исчезнуть из фильтра. Если последняя страница исчезла после редактирования, URL корректируется до последней существующей. Для изначально неверной страницы есть явный переход к доступной.

Детали используют общий с `/rate` контроллер и `RatingControl`: явное сохранение, настоящий 0, отдельная очистка в NULL. Просмотр, Letterboxd, исходные звёзды и даты не перезаписываются. После успешной записи и ошибки чтения повторяется только GET. Чтение библиотеки не вызывает OpenAI/TMDB API; изображения загружаются через прежний разрешённый CDN/Next Image. Новых API, миграций или зависимостей нет.

Проверки с записью выполняются только на синтетической SQLite и отдельном порту с явно заданным `DATABASE_PATH`. `scripts/fixtures/library.ts` программно создаёт 830 тестовых записей; `scripts/library-ui.test.tsx` входит в `npm run test:db`. Рабочую `.env.local` и личную базу для приёмки не менять. Сквозная локальная UX-приёмка фазы 4 выполнена в 4.5; результаты и ограничения приведены выше.

## Поиск и оценивание — подфаза 4.3

`/rate` использует Cinema Spotlight: явный поиск по названию/необязательному году, результаты с постерами и различимыми версиями фильма, панель деталей и оценки. На desktop — две колонки; до 1024 px выбранный фильм заменяет выдачу, а «К результатам» возвращает прежний поиск и фокус. Выбор добавляет только каталог: просмотр подтверждается отдельно. Возможные дубликаты Letterboxd показываются без автоматического связывания.

Шкала — нативный slider 0–100 с крупным числом и синхронным точным вводом. Пустой черновик остаётся «Без оценки» до явного взаимодействия; 0 — реальная оценка. Изменение шкалы не записывает данные. Первое подтверждение может отправить просмотр без оценки; у просмотренного фильма очистка выполняется отдельной кнопкой. Повтор значения сохраняет источник и timestamps. «Неинтересно» визуально отделено от оценки.

`/rate?movie_id=<local ID>` загружает готовый фильм из рекомендаций без повторного поиска и автоматического просмотра. Неверная ссылка/неизвестный ID оставляет поиск доступным. После подтверждения можно явно вернуться к рекомендациям. Ошибки записи сохраняют черновик; если запись выполнена, но чтение не удалось, «Перечитать фильм» делает только GET. Поиск не отправляется при каждом вводе символа; запоздалые ответы не заменяют актуальную выдачу.

API и SQLite-схема прежние; библиотека в 4.4 использует тот же контроллер записи и шкалу без изменения поведения /rate. Приёмка — временная SQLite, моки TMDB и запрещённый OpenAI, браузер 375/430/768/1024/1440 px, клавиатура/drag/touch, ошибки, 0/NULL, Letterboxd и рестарт. Рабочую базу для проверки не менять: используйте отдельный DATABASE_PATH; реальные ключи и персональные файлы в Git не входят.

## Реальные рекомендации в интерфейсе — подфаза 4.2

Главная использует прежние `generateCandidates()` → `rankRecommendations(save:false)` → `recordRecommendations()`. Промпты, ограничения, модель из `OPENAI_MODEL` и самостоятельные CLI сохранены. Обычно это **два платных OpenAI-запроса**; стоимость заранее не рассчитывается. При ошибке нет автоматических повторов или смены модели. Реальная live-приёмка новых подборок пока не выполнялась.

- `GET /api/recommendations` — последняя полноценная группа строго по `result_id`, текущие доступные фильмы, время, количество скрытых/недоступных и безопасное состояние запуска. Чтение только read-only, без миграций и внешних сервисов. Группы ручного внесения и записи без объяснений не становятся AI-подборкой; для `legacy:` время обозначено как время внесения. Исчерпанная последняя группа не заменяется старой.
- `POST /api/recommendations/generate` — JSON `{ "request_id": "UUID", "confirmed": true }`, не более 1 КиБ, с прежней проверкой Origin. Успех — 201, повтор сохранённого запроса — 200, активный/неопределённый запуск — 409; ошибки конфигурации/внешних сервисов/сохранения возвращаются безопасно и не выдают техническую частичную выдачу за успех.
- Экран запрашивает GET при открытии, возврате и восстановлении видимости. Во время подбора сохраняет прежние фильмы и опрашивает только GET. Потеря ответа не вызывает нового платного POST. «Неинтересно» и «Отменить» используют существующие маршруты; «Посмотрел» открывает `/rate?movie_id=<local ID>`, где запись требует отдельного подтверждения, включая оценку 0 или просмотр без оценки.
- Cooldown 30 дней ограничивает **новую генерацию**, а не чтение собственной подборки. При чтении исключаются текущие просмотры/скрытия и недоступные данные; исторический `rejected` после undo не запрещает показ навсегда. Новые оценки учитываются прежними контекстами, профиль автоматически не обновляется.

Перед платным этапом проверяются настройки/профиль/оценки/размер контекста, берётся межпроцессная блокировка, создаётся SQLite backup и применяются миграции. Схема 5 добавляет только nullable `movies.backdrop_path`; чтение совместимо со схемами 3–5. Poster/backdrop приходят из уже выполняемого details, не требуют отдельных запросов и не передаются LLM. Существующим фильмам заполняются только отсутствующие изображения; исходные поля и персональная история сохраняются.

Рядом с SQLite находятся `<database>.recommendations.lock` и приватная `.recommendation-runs/<database-key>/`: атомарные JSON-файлы с состоянием и подготовленным результатом, без профиля, промпта или reasoning. Файлы имеют права 0600, каталог — 0700; исключены из Git. `request_id` переживает перезапуск. После ошибки SQL экран предлагает **«Повторить сохранение без AI»**: тот же JSON отправляется на `POST /api/recommendations/generate?save_only=1`. Этот режим никогда не начинает платные этапы, даже если локальный результат потерян; выполняет новый backup и актуальную валидацию. Повтор ошибочной/неопределённой оплачиваемой попытки не перезапускает её.

Если сервер завершился аварийно, проверьте PID владельца в lock-файле и команду соответствующего процесса. Удалять оставшуюся блокировку можно вручную только после подтверждения, что процесс завершён. Автоматического удаления нет. Гарантия общей блокировки относится к HTTP-конвейеру, а самостоятельные CLI не входят в неё. Приложение ограничивает сетевую работу 15 минутами с AbortSignal; `maxDuration=900` — дополнительная настройка среды. Живой сервер завершает уже подтверждённую операцию после отключения клиента.

Проверки: `npm run test:db`, `npm run lint`, `npm run typecheck`, `npm run build`, `git diff --check`. Автотесты используют временные базы и HTTP-моки. Для ручного запуска с отдельной базой явно задайте `DATABASE_PATH=/absolute/path/test.sqlite` во всех командах; сначала инициализируйте **тестовую** схему и подготовьте синтетический профиль. Обычный `npm run dev -- --port 45143` использует локальные настройки: подтверждение подбора на реальной базе уже расходует API и сохраняет историю. Не используйте его для автоматической приёмки.

## Поиск и каталог — подфаза 3.1

- `GET /api/movies/search?q=Dune` — поиск только фильмов TMDB, на английском; необязательный `year=2021`. Название 1–200 символов, год 1–9999. Ответ `{results:[{id,title,original_title,year,poster_path}],has_more}`: одна страница, максимум 20 уникальных результатов. Результат выбирает владелец, автоматического выбора нет.
- `POST /api/movies` с `Content-Type: application/json` и телом `{"tmdb_id":438631}` — сервер получает details с credits и сохраняет подтверждённые метаданные. Другие поля не принимаются. `201 created` / `200 already_exists` возвращают `movie_id` и `tmdb_id`.
- `409 possible_duplicate` возвращает `matches` с локальными ID, названиями и годами: найдена похожая запись без TMDB ID. Даже единственное совпадение не связывается автоматически; совпадение названия при неизвестном годе также требует ручной проверки.
- Некорректный ввод — 400, отсутствующий фильм TMDB — 404, недоступный TMDB/его конфигурация — 502, ошибка локального каталога — 503. Ответы не кешируются и не содержат секретов.

Повтор по существующему TMDB ID не вызывает TMDB и ничего не перезаписывает. Новая запись не создаёт `user_movies`, просмотр или оценку. Короткий метр и неизвестная длительность разрешены в каталоге, но прежние ограничения рекомендателя сохраняются. OpenAI не используется.

Перед новой вставкой создаётся уникальная SQLite-копия в `backups/` рядом с базой; затем применяются существующие миграции (при необходимости 3→4). Вставка и повторная проверка конфликтов выполняются одной IMMEDIATE-транзакцией. GET не открывает SQLite и не применяет миграции. Новых миграций для каталога нет.

**Проверка без изменений рабочей библиотеки:** `npx tsx --test scripts/movie-catalog.test.ts` использует только синтетические временные базы и моки TMDB. Для самостоятельной HTTP-проверки запустите отдельный сервер с временной базой (поиск/details при этом реально обращаются к TMDB, OpenAI не вызывается):

```sh
npm run db:init
npm run dev -- --port 3001
```

```sh
# Подставьте выбранный ID из результатов:
```

## Просмотр и первая оценка — подфаза 3.2

`POST /api/movies/[id]/watch` принимает **локальный movie_id**, возвращённый добавлением фильма в каталог, а не TMDB ID. Content-Type — application/json, тело не больше 1 КиБ. Метод подтверждает просмотр; принимает только необязательное поле rating_100.

| Тело | Действие |
| --- | --- |
| `{}` или `{"rating_100":null}` | Подтвердить просмотр, сохранив имеющуюся оценку. У новой персональной записи оценка NULL, источник none. |
| `{"rating_100":0}` | Назначить первую настоящую оценку 0/100, источник manual. |
| `{"rating_100":85}` | Назначить первую целочисленную оценку 0–100. |

Повтор того же числа сохраняет прежний источник, включая letterboxd, и timestamps. Если оценка уже есть и передано другое число — 409 rating_already_exists без изменений: редактирование и очистка относятся к 3.3. Передавать watched=false или другие поля нельзя.

Ответ содержит status (created/updated/unchanged), movie_id, watched=true, rating_100 и rating_source. HTTP: 201 — создана персональная строка; 200 — обновление или повтор; 400 — неверный ввод; 404 — неизвестный локальный фильм; 409 — попытка заменить оценку; 500 — техническая ошибка. Все ответы no-store, внутренние ошибки не раскрываются.

Запись атомарна и предваряется уникальным backup рядом с SQLite; миграция 3→4 при необходимости выполняется существующим механизмом. Для неизвестного фильма, конфликта и повторного действия backup/миграции не запускаются. Поля Letterboxd, исходные звёзды, not_interested и исторический rejected сохраняются; дата просмотра не выдумывается. Добавленные в 3.1 фильмы сами по себе не считаются просмотренными — это отдельное действие.

Для отдельного сервера на порту 3001 с временным DATABASE_PATH из предыдущего раздела:

```sh
# Подставьте локальный movie_id из ответа POST /api/movies:
MOVIE_ID=1
# Просмотр без оценки:
curl -X POST "http://127.0.0.1:3001/api/movies/$MOVIE_ID/watch" \
  -H 'Content-Type: application/json' -d '{}'
# Первая оценка, включая 0:
curl -X POST "http://127.0.0.1:3001/api/movies/$MOVIE_ID/watch" \
  -H 'Content-Type: application/json' -d '{"rating_100":0}'
```

Сам watch-маршрут не требует ключей и не вызывает TMDB/OpenAI. Просмотр с NULL немедленно исключает фильм из рекомендаций, но не считается отрицательной оценкой или изменением вкуса. Первая оценка, включая 0, передаётся в следующий контекст кандидатов и ранжирования; порог обновления профиля — 10 отличий. Профиль автоматически не пересоздаётся.

Полностью автономная проверка без изменения реальной библиотеки: `npx tsx --test scripts/movie-watch.test.ts` — временные синтетические базы и HTTP-моки.

## Библиотека и редактирование — подфаза 3.3

- `GET /api/library` — только просмотренные, включая NULL-оценки, историю без TMDB ID, короткий метр и TV из импорта. Само наличие в каталоге и скрытие не означают просмотр. Ответ: `{items,total,page,limit,total_pages}`.
- `GET /api/library/[id]` — сохранённые подробности любого локального фильма. Для каталожного фильма без персональной строки возвращаются watched=false, rating_100=NULL и rating_source=none; строка при чтении не создаётся. Неизвестный ID — 404.
- `PATCH /api/library/[id]/rating` — JSON с единственным обязательным полем rating_100: целое 0–100 или явный null. Только для уже просмотренных: неизвестный фильм — 404, непросмотренный — 409 movie_not_watched. Пропуск поля, строка, дробь или дополнительные поля — 400. Ответ 200: status=updated/unchanged, movie_id, watched=true, rating_100, rating_source. Технические ошибки — безопасный 500.

Параметры списка:

| Параметр | Значения |
| --- | --- |
| q | Необязательная подстрока до 200 символов, без учёта регистра, включая кириллицу/Unicode NFKC. Поиск по исходному, TMDB- и оригинальному названию. `%` и `_` — обычные символы. |
| rated | all (по умолчанию), true (включая 0), false (только NULL). |
| year | Целое 1–9999; исходный год, при отсутствии — сохранённый TMDB-год. |
| page / limit | Страница от 1; размер 1–100, по умолчанию page=1 и limit=25. Пустая/далёкая страница — пустой список. |
| sort | added_desc (по умолчанию), added_asc, rating_desc, rating_asc. NULL-оценки в конце; равенства разрешаются локальным ID по возрастанию. |

Дата добавления — created_at персональной записи, **не дата просмотра**. Элементы возвращают ID, названия/год, постер, жанры/режиссёров, просмотр, текущую оценку/источник, скрытие, URI/исходные звёзды/обе даты Letterboxd и реальные сохранённые даты. Детали дополнительно включают описание, тип/длительность, credits, язык и TMDB-метрики. Неизвестные значения остаются NULL.

GET открывает SQLite только для чтения, без миграций и сетевых запросов. Все ответы no-store. Перед фактическим PATCH создаётся уникальный backup, затем при необходимости применяется существующая миграция 3→4; изменение оценки/источника и повторная проверка просмотра выполняются одной IMMEDIATE-транзакцией. Для ошибки ввода, неизвестного/непросмотренного фильма и no-op backup/миграции не нужны.

Новая оценка получает источник manual; очистка — none. Повтор текущего значения сохраняет timestamps и прежний источник. Не меняются watched=1, not_interested, метаданные и поля Letterboxd, включая original_rating_stars. Очищенная оценка не восстанавливается из звёзд. Контракт первого просмотра 3.2 остаётся прежним.

Пример для отдельной временной базы/сервера на порту 3001 из раздела 3.1, после подтверждения просмотра в 3.2:

```sh
curl 'http://127.0.0.1:3001/api/library?rated=all&limit=25&sort=added_desc'
curl --get http://127.0.0.1:3001/api/library --data-urlencode 'q=Dune'
# Локальный movie_id из результатов, а не TMDB ID:
MOVIE_ID=1
curl "http://127.0.0.1:3001/api/library/$MOVIE_ID"
curl -X PATCH "http://127.0.0.1:3001/api/library/$MOVIE_ID/rating" \
  -H 'Content-Type: application/json' -d '{"rating_100":85}'
curl "http://127.0.0.1:3001/api/library/$MOVIE_ID"
curl -X PATCH "http://127.0.0.1:3001/api/library/$MOVIE_ID/rating" \
  -H 'Content-Type: application/json' -d '{"rating_100":null}'
curl "http://127.0.0.1:3001/api/library/$MOVIE_ID"
```

Изменение и очистка доступны следующему контексту кандидатов/ранжирования через существующие дельты. NULL удаляет актуальное свидетельство, 0 остаётся настоящей оценкой. Фильм после очистки остаётся просмотренным и исключённым; профиль автоматически не пересоздаётся, порог — 10 отличий. API-ключи библиотеке не требуются.

Автономная проверка без изменения рабочей SQLite и внешней сети: `npx tsx --test scripts/library.test.ts`. Редактирование просмотра, удаление фильмов и UI не добавлялись.

## Сквозной рабочий экран и отклонение — подфаза 3.4

Главная страница содержит простые формы: поиск TMDB с выбором года/результата, добавление в каталог, просмотр с необязательной оценкой, поиск библиотеки и страницы, редактирование/очистка, «Неинтересно» и отмена. После записи данные перечитываются без перезапуска Next.js. Пустое поле первого просмотра не означает 0, а очистка существующей оценки выполняется отдельной кнопкой. Возможные дубликаты показываются с локальными кандидатами без автоматического связывания.

Это функциональный экран фазы 3 на базовых HTML-элементах. AI-подборки остаются в CLI; кнопок платной генерации нет. В фазе 4 предстоят финальный дизайн, три раздела и мобильная приёмка.

Новые HTTP-маршруты принимают только JSON до 1 КиБ с единственным положительным целочисленным tmdb_id:

```sh
# Только на отдельном тестовом сервере; ID должен существовать в его каталоге:
curl -X POST http://127.0.0.1:3001/api/recommendations/reject \
  -H 'Content-Type: application/json' -d '{"tmdb_id":438631}'
curl -X POST http://127.0.0.1:3001/api/recommendations/reject/undo \
  -H 'Content-Type: application/json' -d '{"tmdb_id":438631}'
```

Ответ 200: tmdb_id, not_interested, personal_changes, history_changes. Ошибки: 400 — вход, 404 — неизвестный локально ID, 403 — Origin, 500 — запись/backup. Все ответы no-store. Новое отклонение/отмена использует существующий rejectRecommendation, резервную копию и миграционный механизм. Для полного no-op backup/миграция не нужны; повтор также обрабатывает связанные показы, у которых rejected ещё не установлен.

Отклонение устанавливает текущий not_interested и rejected у связанных показов. Оценка, просмотр и объяснения не меняются. Отмена снимает только текущий запрет, сохраняя исторические rejected и 30-дневный cooldown. Ни отклонение, ни его отмена не обращаются к TMDB/OpenAI; для записей без подтверждённого TMDB ID эта операция в экране недоступна.

**Защита изменяющих запросов:** общий JSON-reader проверяет Origin до чтения тела/SQLite во всех POST/PATCH. Явный Origin должен соответствовать протоколу URL и фактическому Host запроса. Host используется из-за нормализации loopback-адресов Next.js; X-Forwarded-Host/Proto напрямую не используются для доверия. Чужой/null/некорректный Origin и Sec-Fetch-Site=cross-site отклоняются с 403. Без Origin разрешены обычный curl без браузерных заголовков и контексты same-origin/none. CORS-разрешения и авторизация не добавлены; приложение рассчитано на доверенную домашнюю сеть.

`npx tsx --test scripts/workflow.test.ts` воспроизводит составные сценарии на временных базах с моками: поиск→просмотр→оценки, сохранённая рекомендация→тот же локальный ID→просмотр, отклонение/отмена/cooldown, ошибки/rollback и Origin. Новая оценка, очищенная до пересчёта профиля, возвращается к отсутствию отличия; очистка оценки, уже находящейся в снимке, фиксируется как cleared. Журнала промежуточных действий нет, профиль автоматически не пересоздаётся.

При приёмке 3.4 отдельно проверен браузер на синтетической базе с моками TMDB: загрузка/успех/пустая выдача/ошибки, 0, изменение/очистка, повторное добавление, конфликт старой записи, отклонение/отмена, устаревший ответ поиска и сохранность после перезапуска. Браузерная консоль не показала необработанных ошибок. HTTP-проверки дополнительно покрыли Origin/Host, отказ backup и SQL rollback. Реальная библиотека не изменялась, внешних AI-вызовов не было.

## AI-профиль вкуса — подфаза 2.1

Безопасный сухой прогон, без ключа и платного API:

```sh
npm run taste:generate -- --dry-run
npm run taste:show
```

Без параметров `taste:generate` тоже выполняет dry-run. Он показывает количество оценок, группы/покрытие метаданными, число подробных примеров и контрастов, размер входа и неточную оценку токенов. `taste:show` читает уже сохранённый профиль и показывает реальные названия из SQLite; в личной базе сохранён профиль v1 на 519 оценках.

Для одного реального анализа сначала настроить `OPENAI_API_KEY` и `OPENAI_MODEL` в локальном окружении/.env.local. Предполагаемый первоначальный выбор — `OPENAI_MODEL=gpt-6.1-sol`; актуальная модель задаётся через OPENAI_MODEL и видна в сохранённом профиле. Проверять доступ нужно для выбранной конфигурации. Другая модель автоматически не выбирается. Используется официальный [Responses API со Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses); [GPT-6.1 Sol поддерживает этот формат](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

```sh
# Один платный анализ — только по явному запуску:
npm run taste:generate -- --live
# Явная перегенерация существующего профиля:
npm run taste:generate -- --live --force
```

Обычный live-запуск повторно использует существующий валидный профиль, даже если он устарел. Изменения оценок/контекста показываются как stale, без автоматического расхода токенов; перегенерация требует --force. --dry-run и --live несовместимы, --force без --live запрещён. Приложение и health не вызывают OpenAI.

В анализ входят **все 519 оценок**, включая 41 произведение без TMDB ID; неоценённые просмотры не используются как отрицательные примеры. До 60 подробных примеров (20 на группу) и 12 контрастов отбираются по подтверждённым данным. Профиль на английском, с положительными/отрицательными закономерностями, контрастами, свидетельствами и неопределённостями.

Лимиты: input + JSON Schema до **120 000 UTF-8 байт**, описание примера до 600 символов, max_output_tokens **12 000**, тайм-аут **180 секунд**. При переполнении сокращаются описания, затем подробные примеры по группам, затем дополнительные контрастные пары; базовые оценки не исключаются. Оценка токенов по bytes/3 приблизительна, стоимость в долларах не рассчитывается. Один запрос, без автоматических повторов: тайм-аут мог возникнуть после списания токенов.

Перед live-запросом создаётся SQLite backup в data/backups. Lock-файл рядом с БД (`<DATABASE_PATH>.taste.lock`) запрещает параллельные генерации и удаляется в finally; после аварийного завершения сначала проверить PID из lock-файла и только затем удалять подтверждённо устаревший lock. Отказ, incomplete, ошибочные ID/оценки, некорректный JSON и изменения входного контекста во время запроса сохраняют старый профиль. Схема SQLite не меняется: единственный результат, снимок оценок, отпечаток, версии, модель и доступные input/output usage сохраняются атомарно внутри taste_profile.profile_json. Полный приватный контекст, ключ и reasoning не логируются.

Результат dry-run на 2026-10-25: 519 оценок (245 high / 151 medium / 123 low), 478 с метаданными, 60 подробных примеров, 12 контрастов, **77 742 байта**, приблизительно **25 914 input tokens**. Лимит токенов на ответ включает бюджет модели; при незавершённом результате профиль не сохраняется.

Владелец создал реальный профиль и выполнил два ранжирования. Положительная общая реакция подтверждена только для первой подборки; индивидуальные оценки интереса и после просмотра не предоставлены. Это не измеренная точность. При реализации 2.4 и аудите 2.5 новых API-запросов не было.

## Кандидаты — подфаза 2.2

```sh
# Без API-вызовов и изменений SQLite; без флагов также dry-run:
npm run candidates:generate -- --dry-run
# Платная генерация — только явным запуском, после отдельного создания профиля:

```

Нужен валидный сохранённый AI-профиль; сейчас профиль v1 доступен. Если профиля нет, dry-run завершится с кодом 1 без автогенерации. Dry-run показывает готовность OPENAI_API_KEY/OPENAI_MODEL/TMDB_API_KEY, состояние профиля, число изменений оценок, примеров и контрастов, размер контекста, приблизительное число токенов и лимиты. Ключи не выводятся. --dry-run и --live несовместимы; других режимов нет.

Один LLM-вызов предлагает до 30 названий/годов. К существующему профилю добавляются до 10 высоких и 10 низких примеров, до 6 контрастов и **все новые, изменённые и очищенные оценки** относительно снимка. Устаревший профиль используется с предупреждением и текущими оценками, без пересоздания. Контекст и схема ограничены 120 000 UTF-8 байтами; сначала сокращаются описания, затем необязательные примеры, контрасты и компактный список исключений. Профиль и изменения оценок не выбрасываются: обязательное переполнение прекращает запрос. Промпт английский, внешние данные передаются отдельно как недоверенные.

Дополнительный источник — первая страница TMDB recommendations для максимум пяти разнообразных высокооценённых полнометражных фильмов. До 25 разных предложений собираются по очереди из этих страниц. LLM-названия проверяются Movie Search с точным годом и нормализованным title/original_title; до пяти страниц, неоднозначные и неполные результаты пропускаются. Все новые ID проверяются movie details с credits. Поиск и details кешируются в памяти запуска.

В итог попадают только подтверждённые movie с длительностью ≥60 минут, годом, описанием и жанрами. Режиссёр, vote_count и popularity могут быть NULL; низкие показатели не означают автоматический запрет малоизвестного кино. Просмотренное с любыми оценками, включая NULL/0, и not_interested исключаются по ID. Для истории без ID сравниваются нормализованные исходное/TMDB/оригинальное названия и год; неизвестный год при совпадении названия ведёт к безопасному пропуску. Состояния просмотра/скрытия повторно читаются перед выводом.

Лимиты запуска: **30 LLM + 25 TMDB предложений, до 55 details-проверок, до 120 фактических TMDB-запросов с повторами, до 40 уникальных результатов**. TMDB вызывается последовательно, с интервалом ≥250 мс, прежними тайм-аутами и rate-limit retries; бюджет проверяется перед каждой HTTP-попыткой. Результаты идут в порядке источников (LLM, затем TMDB), без финального ранжирования. Если оба источника нашли один ID, source=both. Меньше 20 результатов допустимо, случайного дополнения нет.

Live выводит JSON со списком кандидатов, source, причинами исключений, лимитами, количеством запросов и usage OpenAI. Технические ошибки дают код 1 и status=error/partial; частичные результаты явно обозначены. Ошибка OpenAI не подменяется подборкой одного TMDB. Отказ, incomplete и невалидный JSON не запускают повторный LLM-запрос. Модель только из OPENAI_MODEL; store:false, max_output_tokens=12000, тайм-аут 180 секунд.

CLI открывает SQLite **только для чтения**, не применяет миграций, не записывает новые фильмы, профиль или историю рекомендаций. Список существует только в памяти и stdout; перенаправленный приватный JSON следует сохранять внутри игнорируемого data/. Владелец сохранил реальные наборы из 40 и 35 кандидатов; они используются для двух уже полученных подборок. Новые платные вызовы в 2.4 не выполнялись.

После отдельного создания профиля сохранить реальный результат 2.2 можно так (это платная генерация кандидатов, она не выполняется командой ранжирования):


`--silent` убирает служебный npm-заголовок из JSON. Файл должен происходить из проверок 2.2: ранжирование валидирует его поля, но не подтверждает заново метаданные через TMDB. Оригиналы и приватные результаты следует хранить внутри игнорируемого data/.

Dry-run не требует ключа/модели и не обращается к сети: проверяет файл, профиль, актуальную библиотеку и контекст; показывает число допустимых/исключённых кандидатов, примеров и изменений оценок, размер входа, приблизительный токеновый объём и наличие OpenAI-настроек без их значений. Нет сохранённого профиля — понятная ошибка с кодом 1, без автоматической генерации. Сейчас профиль v1 и оба файла кандидатов доступны; dry-run выполняется без API.

Последние выбираются по общему режиссёру, затем общим жанрам и локальному ID, без дублей основной выборки. 0 является настоящей оценкой, NULL не становится отрицательным сигналом; свидетельства без TMDB ID остаются доступны по реальным данным SQLite. Устаревший профиль используется с предупреждением и приоритетом текущих оценок.

Сокращаются описания кандидатов 1200→600→300→0, затем описания примеров 600→300→150→0, затем дополнительные связанные примеры, симметрично high/low-примеры и дополнительные контрасты. Live делает ровно один Responses-запрос существующим клиентом: OPENAI_MODEL, strict Structured Outputs, store:false, 180 секунд, максимум 12 000 output tokens. Без TMDB, повторов, смены модели и автоматического исправления ответа. Английский промпт требует персональных положительных/отрицательных закономерностей, контрастов и осторожных причинных гипотез, запрещает вымышленные факты/вероятности. Популярность не заменяет соответствие вкусу.

Результат — 1–5 фильмов в порядке LLM с title/year/TMDB ID, why_fit (до 1000 символов), possible_mismatch (до 600), 1–6 уникальными evidence {movie_id,rating_100} и разрешёнными из SQLite названиями свидетельств. Сервер проверяет схему, принадлежность ID переданному списку, дубли, тексты и точные текущие оценки из переданного контекста; чужие ID и невалидные элементы исключаются. Сразу перед выдачей повторно читаются просмотр/скрытие (включая историю без TMDB ID) и оценки свидетельств. Изменённое/очищенное свидетельство исключает рекомендацию. Корректный неполный список успешен; при отсутствии валидных результатов или API/refusal/incomplete/JSON-ошибке — код 1 без подмены случайными фильмами. Вывод содержит диагностику, модель и фактический usage при наличии, без ключа, полного контекста и reasoning.

Без --save ничего не записывается в movies, user_movies, taste_profile или recommendations. Явное --live --save добавляет память рекомендаций, описанную ниже. Проверка структурированных ссылок подтверждает существование примеров и оценки, **но не доказывает истинность всех свободных объяснений и художественное качество**. Два реальных read-only отбора не записали историю; общая положительная обратная связь подтверждена для первого. Известный usage приведён в аудите 2.5 ниже; новых вызовов при аудите не было.

## Память рекомендаций — подфаза 2.4

```sh
npm run recommendations:history
npm run taste:status
# Существующий read-only режим, один платный отбор:
npm run recommendations:rank -- --input data/candidates.json --live
# Один платный отбор с явной записью успешных результатов:
npm run recommendations:rank -- --input data/candidates.json --live --save
```

Без --save прежнее read-only поведение сохраняется. --save разрешён только вместе с явным --live; dry-run никогда не записывает базу. Новые записывающие команды создают уникальный SQLite backup рядом с базой в backups/ (по умолчанию data/backups/). Для live --save backup выполняется до OpenAI: при его ошибке токены не расходуются. Неприменённые миграции (включая 4/5) в самостоятельном CLI применяются после успешного ранжирования либо при явной записи/отклонении; HTTP-конвейер 4.2 мигрирует после backup до платных этапов. Обычное чтение работает на схемах 3–5.

История сохраняется в recommendations. Новая колонка result_id и уникальный индекс защищают один результат от повторного сохранения. Приложение добавляет к успешному ранжированию UUID result_id и generated_at в UTC. Сохранение — одна IMMEDIATE-транзакция с повторной проверкой просмотра, скрытия, недавних показов и оценок свидетельств. Новый фильм получает проверенные метаданные из файла 2.2, существующий используется по TMDB ID без перезаписи исходных полей (4.2 разрешает только заполнить отсутствующие изображения). Персональные строки ради рекомендации не создаются, оценки/данные Letterboxd не меняются. Ошибка SQL откатывает все новые фильмы и рекомендации.

Повтор уже записанного result_id — no-op, даже если первый раз часть фильмов была пропущена. В JSON отображаются save.saved_count, already_saved_count, would_save_count и причины skipped. При ошибке записи остаются валидированный результат, UUID и usage, save.status=error; CLI завершится с кодом 1. Автоматического повторного LLM-вызова нет.

**Повторы:** серверная константа RECOMMENDATION_REPEAT_DAYS=30 задаёт 30×24 часа от последнего сохранённого показа. Такие фильмы исключаются в генерации и до платного ранжирования, включая старые JSON-файлы кандидатов; перед выдачей/записью история перечитывается. Причина — recently_recommended. Фильтр не ослабляется ради пяти результатов: список может быть меньше или пуст, с диагностикой. На точной границе 30 дней фильм снова допустим. Отклонённые исключаются независимо от даты.

### Внести две прежние подборки без API

Предварительный просмотр (он же режим по умолчанию):

```sh
npm run recommendations:record -- --input data/candidates.json --tmdb-ids 13398,107985,840430,698948,24128 --dry-run
npm run recommendations:record -- --input data/candidates-round2.json --tmdb-ids 10386,445571,500664,24238,3482 --dry-run
```

Для записи владелец заменяет --dry-run на --save. **Эти десять фильмов в рабочую базу автоматически не вносились.** Каждый ID должен присутствовать в валидированном файле кандидатов; сетевых запросов нет. Стабильный ключ из отсортированного набора ID делает повтор безопасным. Старые объяснения отсутствуют, поэтому сохраняются NULL; дата обозначает момент явного внесения, а не неизвестное точное время первоначального показа.

Сохранённый успешный результат ранжирования можно записать или повторить после ошибки SQLite без новой оплаты:

```sh
# При сохранении stdout платного запуска использовать npm run --silent:
# npm run --silent recommendations:rank -- --input data/candidates.json --live --save > data/ranking.json
npm run recommendations:record -- --input data/candidates.json --result data/ranking.json --dry-run
npm run recommendations:record -- --input data/candidates.json --result data/ranking.json --save
```

--result и --tmdb-ids несовместимы. Исходные объяснения и result_id сохраняются; для старого результата без UUID используется стабильный хеш содержимого. Ошибка/пустой результат не записываются, ID и текущие свидетельства проверяются заново. --save и --dry-run несовместимы. Файлы, база и backup игнорируются Git.

### «Неинтересно» и отмена

```sh
npm run recommendations:reject -- --tmdb-id 13398
npm run recommendations:reject -- --tmdb-id 13398 --undo
```

Команда работает только для известного локального фильма; если его нет, сначала явно внести проверенный показ через record. Одной транзакцией not_interested=1 устанавливается в user_movies, а у связанных показов rejected=1. Если персональной строки нет, она создаётся с watched=0, rating_100=NULL, rating_source=none. Существующие оценки/звёзды/просмотр не меняются, нулевая оценка не создаётся. Повторное отклонение безопасно.

--undo снимает текущий not_interested, сохраняя rejected в истории как факт прошлого отклонения. Будущие фильтры используют текущий глобальный флаг, а не исторический rejected. После отмены период 30 дней продолжает действовать. history выводит оба признака, название, год, TMDB ID, дату и доступные объяснения; JSON-файлы кандидатов для чтения истории не нужны.

### Когда обновлять вкус

`taste:status` читает существующее сравнение с ratings_snapshot: added/changed/cleared, total_changes, threshold=10, статус current/stale/refresh_recommended и явную команду обновления. Каждый фильм считается один раз по итоговому состоянию. NULL→0, изменение старой оценки и очистка учитываются; возврат к исходной оценке убирает отличие. Просмотр без оценки, сохранение рекомендации и not_interested не становятся отрицательной оценкой и не увеличивают счётчик. Изменение отпечатка без дельт также показывает stale.

При ≥10 отличиях рекомендуется `npm run taste:generate -- --live --force`. Эта команда остаётся отдельным явным платным действием, никогда не запускается автоматически. В сводках кандидатов и ранжирования добавлен profile_refresh; прежние cache/profile_status сохранены. Новые оценки продолжают поступать в следующий запрос независимо от полного пересчёта профиля.

На 2026-10-26: профиль current, изменений 0, рабочая история рекомендаций пуста, схема остаётся 3 до явной записи. На временной копии проверены обе реальные подборки: 10 вставок, повтор — 0 новых, прежние данные/профиль сохранены. Аудит 2.5 описан ниже; серверный каталог 3.1 описан в разделе поиска.

Десять результатов — разные подтверждённые кандидаты 1964–2023 годов с длительностью 86–147 минут. В исходных 40 кандидатах 25 LLM / 15 TMDB / 0 both; все десять выбранных пришли от LLM. Исходные why_fit/possible_mismatch/evidence двух ранжирований не найдены. Качество их формулировок и частоты ссылок нельзя проверить или восстановить из названий. Оценки четырёх упомянутых опорных фильмов подтверждены SQLite, но это не доказывает силу аналогий.
