# Personal Movie Recommender

Личное веб-приложение для рекомендаций полнометражного кино по истории оценок владельца. Цель будущего рекомендателя — находить фильмы с личной оценкой 80/100 и выше; это не гарантия результата.

**Статус на 2026-10-26:** фаза 2 технически готова как CLI-прототип, аудит 2.5 завершён в пределах доступных данных. Есть профиль v1 на 519 оценках и две реальные подборки; положительная общая реакция подтверждена для первой. Полные тексты объяснений не сохранены, индивидуальные оценки после просмотра отсутствуют. Рабочая история показов ещё пуста; фаза 3 не начата.

## Локальный запуск

Нужны Node.js ≥22 и npm; проверено на Node.js 26.11.1 / npm 11.20.0. Проект использует Next.js App Router, TypeScript и better-sqlite3 без ORM.

```sh
npm install
# Только при отсутствии своего .env.local:
cp -n .env.example .env.local
npm run db:init
npm run db:check
npm run dev
```

Открыть [localhost:3000](http://localhost:3000). Пока доступна стартовая страница Movie Recommender и `GET /api/health`. Dev и production-сервер по умолчанию слушают только 127.0.0.1.

Для production-запуска локально:

```sh
npm run build
npm run start
```

SQLite по умолчанию хранится в `data/movies.sqlite`, отдельно от сборки. `DATABASE_PATH` может быть абсолютным или относительным от корня проекта. `db:init` применяет миграции без очистки данных; запуск приложения сам миграции не выполняет.

## Первоначальные данные

Личные исходники размещаются в `data/import/watched(6).csv` и `data/import/ratings(6).csv`. Их нет в Git. Команда разработчика для первоначального заполнения:

```sh
npm run seed:letterboxd
# Либо указать пути:
npm run seed:letterboxd -- --watched /path/watched.csv --ratings /path/ratings.csv
```

Повторный запуск не создаёт дубликаты и не заменяет существующие персональные записи, включая ручные и очищенные оценки. `0` — реальная оценка, `NULL` — отсутствие оценки. Даты двух CSV хранятся отдельно и не считаются подтверждённой датой просмотра.

Импорт сохраняет всю историю, включая короткометражки и произведения, не найденные в Movie Search. В будущем рекомендателе будут допустимы только фильмы с подтверждённой длительностью от 60 минут.

## TMDB

Настроить настоящий API key v3 в серверной переменной `TMDB_API_KEY` в `.env.local`. Ключ в Git и чат не добавлять. Поиск и метаданные используют английский `en-US`; названия, годы и URI Letterboxd остаются неизменными.

```sh
npm run tmdb:enrich -- --dry-run --limit 10
npm run tmdb:enrich -- --limit 10
npm run tmdb:enrich
```

Сначала проверить кандидатов dry-run: он не меняет SQLite. Обычный запуск создаёт резервную копию, применяет миграции и сохраняет прогресс по каждому произведению. Повторный запуск пропускает успешно обработанные и нерешённые записи. Для осознанной повторной проверки нерешённых есть `--retry-unresolved`; эта команда не исправляет неоднозначности автоматически.

Текущая личная база: **830 просмотров, 519 оценок, 311 без оценки**. С TMDB сопоставлены **756** произведений; **33** неоднозначны, **41** без точного соответствия. Все 830 сохранены. Отсутствие ID не означает отсутствия произведения в TMDB. Отчёты находятся в `data/import-reports/` и `data/tmdb-reports/`, бэкапы — в `data/backups/`.

## AI-профиль вкуса — подфаза 2.1

Безопасный сухой прогон, без ключа и платного API:

```sh
npm run taste:generate -- --dry-run
npm run taste:show
```

Без параметров `taste:generate` тоже выполняет dry-run. Он показывает количество оценок, группы/покрытие метаданными, число подробных примеров и контрастов, размер входа и неточную оценку токенов. `taste:show` читает уже сохранённый профиль и показывает реальные названия из SQLite; в личной базе сохранён профиль v1 на 519 оценках.

Для одного реального анализа сначала настроить `OPENAI_API_KEY` и `OPENAI_MODEL` в локальном окружении/.env.local. Предполагаемый первоначальный выбор — `OPENAI_MODEL=gpt-6.1-sol`; актуальная модель задаётся через OPENAI_MODEL и видна в сохранённом профиле. Проверять доступ нужно для выбранной конфигурации. Другая модель автоматически не выбирается. Используется официальный [Responses API со Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses); [GPT-6.1 Sol поддерживает этот формат](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

```sh
# Один платный анализ — только по явному запуску:
npm run taste:generate -- --live
# Явная перегенерация существующего профиля:
npm run taste:generate -- --live --force
```

Обычный live-запуск повторно использует существующий валидный профиль, даже если он устарел. Изменения оценок/контекста показываются как stale, без автоматического расхода токенов; перегенерация требует --force. --dry-run и --live несовместимы, --force без --live запрещён. Приложение и health не вызывают OpenAI.

В анализ входят **все 519 оценок**, включая 41 произведение без TMDB ID; неоценённые просмотры не используются как отрицательные примеры. До 60 подробных примеров (20 на группу) и 12 контрастов отбираются по подтверждённым данным. Профиль на английском, с положительными/отрицательными закономерностями, контрастами, свидетельствами и неопределённостями.

Лимиты: input + JSON Schema до **120 000 UTF-8 байт**, описание примера до 600 символов, max_output_tokens **12 000**, тайм-аут **180 секунд**. При переполнении сокращаются описания, затем подробные примеры по группам, затем дополнительные контрастные пары; базовые оценки не исключаются. Оценка токенов по bytes/3 приблизительна, стоимость в долларах не рассчитывается. Один запрос, без автоматических повторов: тайм-аут мог возникнуть после списания токенов.

Перед live-запросом создаётся SQLite backup в data/backups. Lock-файл рядом с БД (`<DATABASE_PATH>.taste.lock`) запрещает параллельные генерации и удаляется в finally; после аварийного завершения сначала проверить PID из lock-файла и только затем удалять подтверждённо устаревший lock. Отказ, incomplete, ошибочные ID/оценки, некорректный JSON и изменения входного контекста во время запроса сохраняют старый профиль. Схема SQLite не меняется: единственный результат, снимок оценок, отпечаток, версии, модель и доступные input/output usage сохраняются атомарно внутри taste_profile.profile_json. Полный приватный контекст, ключ и reasoning не логируются.

Результат dry-run на 2026-10-25: 519 оценок (245 high / 151 medium / 123 low), 478 с метаданными, 60 подробных примеров, 12 контрастов, **77 742 байта**, приблизительно **25 914 input tokens**. Лимит токенов на ответ включает бюджет модели; при незавершённом результате профиль не сохраняется.

Владелец создал реальный профиль и выполнил два ранжирования. Положительная общая реакция подтверждена только для первой подборки; индивидуальные оценки интереса и после просмотра не предоставлены. Это не измеренная точность. При реализации 2.4 и аудите 2.5 новых API-запросов не было.

## Кандидаты — подфаза 2.2

```sh
# Без API-вызовов и изменений SQLite; без флагов также dry-run:
npm run candidates:generate -- --dry-run
# Платная генерация — только явным запуском, после отдельного создания профиля:
npm run candidates:generate -- --live
```

Нужен валидный сохранённый AI-профиль; сейчас профиль v1 доступен. Если профиля нет, dry-run завершится с кодом 1 без автогенерации. Dry-run показывает готовность OPENAI_API_KEY/OPENAI_MODEL/TMDB_API_KEY, состояние профиля, число изменений оценок, примеров и контрастов, размер контекста, приблизительное число токенов и лимиты. Ключи не выводятся. --dry-run и --live несовместимы; других режимов нет.

Один LLM-вызов предлагает до 30 названий/годов. К существующему профилю добавляются до 10 высоких и 10 низких примеров, до 6 контрастов и **все новые, изменённые и очищенные оценки** относительно снимка. Устаревший профиль используется с предупреждением и текущими оценками, без пересоздания. Контекст и схема ограничены 120 000 UTF-8 байтами; сначала сокращаются описания, затем необязательные примеры, контрасты и компактный список исключений. Профиль и изменения оценок не выбрасываются: обязательное переполнение прекращает запрос. Промпт английский, внешние данные передаются отдельно как недоверенные.

Дополнительный источник — первая страница TMDB recommendations для максимум пяти разнообразных высокооценённых полнометражных фильмов. До 25 разных предложений собираются по очереди из этих страниц. LLM-названия проверяются Movie Search с точным годом и нормализованным title/original_title; до пяти страниц, неоднозначные и неполные результаты пропускаются. Все новые ID проверяются movie details с credits. Поиск и details кешируются в памяти запуска.

В итог попадают только подтверждённые movie с длительностью ≥60 минут, годом, описанием и жанрами. Режиссёр, vote_count и popularity могут быть NULL; низкие показатели не означают автоматический запрет малоизвестного кино. Просмотренное с любыми оценками, включая NULL/0, и not_interested исключаются по ID. Для истории без ID сравниваются нормализованные исходное/TMDB/оригинальное названия и год; неизвестный год при совпадении названия ведёт к безопасному пропуску. Состояния просмотра/скрытия повторно читаются перед выводом.

Лимиты запуска: **30 LLM + 25 TMDB предложений, до 55 details-проверок, до 120 фактических TMDB-запросов с повторами, до 40 уникальных результатов**. TMDB вызывается последовательно, с интервалом ≥250 мс, прежними тайм-аутами и rate-limit retries; бюджет проверяется перед каждой HTTP-попыткой. Результаты идут в порядке источников (LLM, затем TMDB), без финального ранжирования. Если оба источника нашли один ID, source=both. Меньше 20 результатов допустимо, случайного дополнения нет.

Live выводит JSON со списком кандидатов, source, причинами исключений, лимитами, количеством запросов и usage OpenAI. Технические ошибки дают код 1 и status=error/partial; частичные результаты явно обозначены. Ошибка OpenAI не подменяется подборкой одного TMDB. Отказ, incomplete и невалидный JSON не запускают повторный LLM-запрос. Модель только из OPENAI_MODEL; store:false, max_output_tokens=12000, тайм-аут 180 секунд.

CLI открывает SQLite **только для чтения**, не применяет миграций, не записывает новые фильмы, профиль или историю рекомендаций. Список существует только в памяти и stdout; перенаправленный приватный JSON следует сохранять внутри игнорируемого data/. Владелец сохранил реальные наборы из 40 и 35 кандидатов; они используются для двух уже полученных подборок. Новые платные вызовы в 2.4 не выполнялись.

## Финальное ранжирование — подфаза 2.3

```sh
# Нужны уже сохранённые кандидаты и профиль; без флага также dry-run:
npm run recommendations:rank -- --input data/candidates.json --dry-run
# Один платный отбор — только явным запуском владельца:
npm run recommendations:rank -- --input data/candidates.json --live
```

Ранжирование не создаёт профиль и не запускает поиск кандидатов. Без --save оно читает SQLite в read-only режиме и принимает сохранённый JSON-результат 2.2: mode=live, status=ok/partial, максимум 40 уникальных TMDB ID. Partial-вход допускается с предупреждением. В MovieCandidate добавлено явное media_type=movie; файлы без него требуют нового вывода генератора, тип фильма не угадывается. Невалидные записи, TV/короткий метр, неизвестная длительность, просмотренные и скрытые исключаются до API с диагностикой. Повторные входные ID, более 40 записей и повреждённый JSON прекращают запуск.

После отдельного создания профиля сохранить реальный результат 2.2 можно так (это платная генерация кандидатов, она не выполняется командой ранжирования):

```sh
npm run --silent candidates:generate -- --live > data/candidates.json
```

`--silent` убирает служебный npm-заголовок из JSON. Файл должен происходить из проверок 2.2: ранжирование валидирует его поля, но не подтверждает заново метаданные через TMDB. Оригиналы и приватные результаты следует хранить внутри игнорируемого data/.

Dry-run не требует ключа/модели и не обращается к сети: проверяет файл, профиль, актуальную библиотеку и контекст; показывает число допустимых/исключённых кандидатов, примеров и изменений оценок, размер входа, приблизительный токеновый объём и наличие OpenAI-настроек без их значений. Нет сохранённого профиля — понятная ошибка с кодом 1, без автоматической генерации. Сейчас профиль v1 и оба файла кандидатов доступны; dry-run выполняется без API.

В контекст входят профиль, все новые/изменённые/очищенные оценки относительно его снимка, до 10 high/10 low примеров, до 6 контрастов и до 10 дополнительных связанных примеров. Последние выбираются по общему режиссёру, затем общим жанрам и локальному ID, без дублей основной выборки. 0 является настоящей оценкой, NULL не становится отрицательным сигналом; свидетельства без TMDB ID остаются доступны по реальным данным SQLite. Устаревший профиль используется с предупреждением и приоритетом текущих оценок.

Лимит input + JSON Schema — **120 000 UTF-8 байт**. Сокращаются описания кандидатов 1200→600→300→0, затем описания примеров 600→300→150→0, затем дополнительные связанные примеры, симметрично high/low-примеры и дополнительные контрасты. Профиль, все изменения оценок и основные поля всех допустимых кандидатов не отбрасываются; невместимый обязательный контекст останавливает запрос.

Live делает ровно один Responses-запрос существующим клиентом: OPENAI_MODEL, strict Structured Outputs, store:false, 180 секунд, максимум 12 000 output tokens. Без TMDB, повторов, смены модели и автоматического исправления ответа. Английский промпт требует персональных положительных/отрицательных закономерностей, контрастов и осторожных причинных гипотез, запрещает вымышленные факты/вероятности. Популярность не заменяет соответствие вкусу.

Результат — 1–5 фильмов в порядке LLM с title/year/TMDB ID, why_fit (до 1000 символов), possible_mismatch (до 600), 1–6 уникальными evidence {movie_id,rating_100} и разрешёнными из SQLite названиями свидетельств. Сервер проверяет схему, принадлежность ID переданному списку, дубли, тексты и точные текущие оценки из переданного контекста; чужие ID и невалидные элементы исключаются. Сразу перед выдачей повторно читаются просмотр/скрытие (включая историю без TMDB ID) и оценки свидетельств. Изменённое/очищенное свидетельство исключает рекомендацию. Корректный неполный список успешен; при отсутствии валидных результатов или API/refusal/incomplete/JSON-ошибке — код 1 без подмены случайными фильмами. Вывод содержит диагностику, модель и фактический usage при наличии, без ключа, полного контекста и reasoning.

Без --save ничего не записывается в movies, user_movies, taste_profile или recommendations. Явное --live --save добавляет память рекомендаций, описанную ниже. Проверка структурированных ссылок подтверждает существование примеров и оценки, **но не доказывает истинность всех свободных объяснений и художественное качество**. Два реальных read-only отбора не записали историю; общая положительная обратная связь подтверждена для первого. Известный usage приведён в аудите 2.5 ниже; новых вызовов при аудите не было.

## Память рекомендаций — подфаза 2.4

```sh
npm run recommendations:history
npm run taste:status
# Существующий read-only режим, один платный отбор:
npm run recommendations:rank -- --input data/candidates.json --live
# Один платный отбор с явной записью успешных результатов:
npm run recommendations:rank -- --input data/candidates.json --live --save
```

Без --save прежнее read-only поведение сохраняется. --save разрешён только вместе с явным --live; dry-run никогда не записывает базу. Новые записывающие команды создают уникальный SQLite backup рядом с базой в backups/ (по умолчанию data/backups/). Для live --save backup выполняется до OpenAI: при его ошибке токены не расходуются. Миграция 4 применяется только после успешного ранжирования либо при явной записи/отклонении. Обычное чтение работает на схемах 3 и 4.

История сохраняется в recommendations. Новая колонка result_id и уникальный индекс защищают один результат от повторного сохранения. Приложение добавляет к успешному ранжированию UUID result_id и generated_at в UTC. Сохранение — одна IMMEDIATE-транзакция с повторной проверкой просмотра, скрытия, недавних показов и оценок свидетельств. Новый фильм получает проверенные метаданные из файла 2.2, существующий используется по TMDB ID без перезаписи. Персональные строки ради рекомендации не создаются, оценки/данные Letterboxd не меняются. Ошибка SQL откатывает все новые фильмы и рекомендации.

Повтор уже записанного result_id — no-op, даже если первый раз часть фильмов была пропущена. В JSON отображаются save.saved_count, already_saved_count, would_save_count и причины skipped. При ошибке записи остаются валидированный результат, UUID и usage, save.status=error; CLI завершится с кодом 1. Автоматического повторного LLM-вызова нет.

**Повторы:** серверная константа RECOMMENDATION_REPEAT_DAYS=30 задаёт 30×24 часа от последнего сохранённого показа. Такие фильмы исключаются в генерации и до платного ранжирования, включая старые JSON-файлы кандидатов; перед выдачей/записью история перечитывается. Причина — recently_recommended. Фильтр не ослабляется ради пяти результатов: список может быть меньше или пуст, с диагностикой. На точной границе 30 дней фильм снова допустим. Отклонённые исключаются независимо от даты.

### Внести две прежние подборки без API

Предварительный просмотр (он же режим по умолчанию):

```sh
npm run recommendations:record -- --input data/candidates.json --tmdb-ids 13398,107985,840430,698948,24128 --dry-run
npm run recommendations:record -- --input data/candidates-round2.json --tmdb-ids 10386,445571,500664,24238,3482 --dry-run
```

Для записи владелец заменяет --dry-run на --save. **Эти десять фильмов в рабочую базу автоматически не вносились.** Каждый ID должен присутствовать в валидированном файле кандидатов; сетевых запросов нет. Стабильный ключ из отсортированного набора ID делает повтор безопасным. Старые объяснения отсутствуют, поэтому сохраняются NULL; дата обозначает момент явного внесения, а не неизвестное точное время первоначального показа.

Сохранённый успешный результат ранжирования можно записать или повторить после ошибки SQLite без новой оплаты:

```sh
# При сохранении stdout платного запуска использовать npm run --silent:
# npm run --silent recommendations:rank -- --input data/candidates.json --live --save > data/ranking.json
npm run recommendations:record -- --input data/candidates.json --result data/ranking.json --dry-run
npm run recommendations:record -- --input data/candidates.json --result data/ranking.json --save
```

--result и --tmdb-ids несовместимы. Исходные объяснения и result_id сохраняются; для старого результата без UUID используется стабильный хеш содержимого. Ошибка/пустой результат не записываются, ID и текущие свидетельства проверяются заново. --save и --dry-run несовместимы. Файлы, база и backup игнорируются Git.

### «Неинтересно» и отмена

```sh
npm run recommendations:reject -- --tmdb-id 13398
npm run recommendations:reject -- --tmdb-id 13398 --undo
```

Команда работает только для известного локального фильма; если его нет, сначала явно внести проверенный показ через record. Одной транзакцией not_interested=1 устанавливается в user_movies, а у связанных показов rejected=1. Если персональной строки нет, она создаётся с watched=0, rating_100=NULL, rating_source=none. Существующие оценки/звёзды/просмотр не меняются, нулевая оценка не создаётся. Повторное отклонение безопасно.

--undo снимает текущий not_interested, сохраняя rejected в истории как факт прошлого отклонения. Будущие фильтры используют текущий глобальный флаг, а не исторический rejected. После отмены период 30 дней продолжает действовать. history выводит оба признака, название, год, TMDB ID, дату и доступные объяснения; JSON-файлы кандидатов для чтения истории не нужны.

### Когда обновлять вкус

`taste:status` читает существующее сравнение с ratings_snapshot: added/changed/cleared, total_changes, threshold=10, статус current/stale/refresh_recommended и явную команду обновления. Каждый фильм считается один раз по итоговому состоянию. NULL→0, изменение старой оценки и очистка учитываются; возврат к исходной оценке убирает отличие. Просмотр без оценки, сохранение рекомендации и not_interested не становятся отрицательной оценкой и не увеличивают счётчик. Изменение отпечатка без дельт также показывает stale.

При ≥10 отличиях рекомендуется `npm run taste:generate -- --live --force`. Эта команда остаётся отдельным явным платным действием, никогда не запускается автоматически. В сводках кандидатов и ранжирования добавлен profile_refresh; прежние cache/profile_status сохранены. Новые оценки продолжают поступать в следующий запрос независимо от полного пересчёта профиля.

На 2026-10-26: профиль current, изменений 0, рабочая история рекомендаций пуста, схема остаётся 3 до явной записи. На временной копии проверены обе реальные подборки: 10 вставок, повтор — 0 новых, прежние данные/профиль сохранены. Аудит 2.5 описан ниже; фаза 3 не начата.

## Аудит 2.5 и границы готовности

Все 113 тестов, lint, TypeScript и production build проходят. На временной SQLite-копии проверены память, повторное сохранение, граница 30 дней, отклонения и следующий вход модели при новых оценках 100/20, изменении, очистке и достижении порога 10. Основная база и исходные JSON не менялись, новых API-запросов нет. Производственный алгоритм и промпты не изменены: подтверждённых ошибок аудит не выявил.

Десять результатов — разные подтверждённые кандидаты 1964–2023 годов с длительностью 86–147 минут. В исходных 40 кандидатах 25 LLM / 15 TMDB / 0 both; все десять выбранных пришли от LLM. Вторые 35 — подмножество первого набора, а не независимая генерация: скопированный usage нельзя учитывать второй раз. LLM-кандидаты ограничением 40 не вытеснялись; пять проверенных TMDB-кандидатов не вошли из-за предусмотренного приоритета основного источника.

Известные расходы: профиль 19 300/3 921, генерация кандидатов 17 397/822, первое ранжирование 16 840/1 410, второе 16 028/1 586 input/output tokens. **Сумма известных операций — 69 565 input и 7 739 output**, не полный расход аккаунта; долларовая стоимость не вычислялась.

Исходные why_fit/possible_mismatch/evidence двух ранжирований не найдены. Качество их формулировок и частоты ссылок нельзя проверить или восстановить из названий. Оценки четырёх упомянутых опорных фильмов подтверждены SQLite, но это не доказывает силу аналогий. Мотив спасения у Thirteen Lives и Django Unchained слишком общий для самостоятельного доказательства личного соответствия; без исходного текста это гипотеза, не подтверждённая ошибка. Второй подборке и отдельным фильмам пользовательские оценки не присваиваются.
